# scripts

The factory's own scripts: `spawn.sh`, which starts and resumes every factory session, `link-skills.sh`, which installs the skills, the herdr servers' ops job, a worktree's `node_modules` clone and `bun run test:skills`.
AGENTS.md keeps one line for each, and this file holds the text that line stands for.
It also holds `bun run hooks:differential`, the sweep and replay a hook PR's Evidence quotes, the rule for an edit script's replacements, a zsh loop's variable names, and where a factory script's orphan is ended.
Read a section before you change its script or its tests, or when it refuses a start you did not expect.
The factory's hooks are in [hooks/README.md](./hooks/README.md).

## spawn.sh

- While `playground focus` stands (the data folder's `focus.json`, playbook's LIFECYCLE.md), spawn.sh refuses every start, naming focus's session and its end, but two: a reviewer or tester that reports to the focused session (a resume's, the worker its roster row names),

  Each one passes focus, and the gates SPAWN.md's Capacity gate names for a priority start.
- A session opens a priority window only with `playground priority on <session> --reason "<why>"`, which writes `priority-<session>.json` naming the session, who opened it, the reason and the time, and lifts it with `playground priority off <session> --reason "<why>"`; a window written by hand passes no review of who opened it or why.
  spawn.sh reads a window through `run-slot.sh window`, the queue's own reader, so it passes only the `--priority` start of the session it names, and a priority file that is no JSON object passes none: lift it once that start is done.
  A lead opens one only on the owner's or the dispatcher's word, never on its own.
  Each `on`, `off` and lapse is a line in the data folder's `ops/priority.log`, and ops-tick's `priority-lapse` beat lifts a window still standing after `LAPSE_HOURS` (`packages/scripts/src/playground/priority.ts`), telling ops, so a forgotten window stops passing starts by itself.

## The herdr servers

- The herdr servers belong to one ops job, `bun run ops:herdr` (`packages/scripts/src/ops-herdr/`): it starts each that is down on the binary the repo's `pin.json` beside it names, with its `config.toml`, so both change only through a merged PR, and `bun run ops:herdr stop <session>` refuses while the session holds a pane, since a stop exits every pane;
  `stop default` stops herdr's own default server (`~/.config/herdr/herdr.sock`), which no job starts, refusing only while one of its panes runs an agent.
  The binary is Playground's own copy at `~/.playground/bin/herdr`, following HOME alone as the sockets do, and `playground herdr pin` (`packages/scripts/src/playground/herdr-pin.ts`) puts it there: it downloads the pinned version's release asset for this machine, checks its SHA-256 against the pin before the move, and refuses a mismatch naming both sums.
  The pin holds GitHub's digest of each release asset, keyed `darwin-arm64`, `darwin-x64`, `linux-arm64` and `linux-x64`, and the job takes this machine's, refusing a machine the pin names no asset for; a herdr on PATH is the human's own, which nothing runs.
  Moving to a new herdr is a PR to `pin.json`: its version and every asset's sum.
  Once it has started a server, any of `PLAYGROUND_HERDR_SESSIONS` (`playground,playground-probes` by default; a name that is not a word is named on its beat and skipped), it runs `spawn.sh restore` pointed at that server, since the pinned config turns herdr's own resume off,
  and prints one line of counts for it once (`restoreLines` for a restore that exited 0, a gate's waits included, `restoreProblem` on the beat for one that failed, both in `packages/scripts/src/ops-herdr/herdr.ts`), each session's own line kept in `<server>.restore.log` beside the server's socket.

  A person brings herdr back with bare `playground`, which runs its `start` first.
  A server hands its panes the shell basics alone, so `spawn.sh`'s herdr launch file sets `TMPDIR` to `$(getconf DARWIN_USER_TEMP_DIR)`, keeping one already set, or on Linux, whose `getconf` has no such name, to the session's own folder spawn.sh's `mktemp -d` made under `/tmp`, over any inherited one,

## Shared git hooks and the turbo cache

- Every worktree shares one `.git/hooks`, and lefthook.yml's `lefthook: bun node_modules/.bin/lefthook` makes each hook run the committing worktree's own lefthook, never the binary of whichever worktree last ran `bun install` (which goes when that worktree is removed).
  So a worktree commits, pushes or merges once it has run `bun install`; one that stops on `error: Script not found "node_modules/.bin/lefthook"` needs it.
  lefthook rewrites the shared hooks whenever the committing worktree's config differs from the last install's, so a worktree branched before this setting puts the old hook back on its next commit until it rebases onto `canary`.
- turbo.json's `cacheDir` keeps each worktree's turbo cache inside that worktree (turbo would otherwise share the main checkout's `.turbo/cache`), so no build, dev stack or pre-commit hook in a worktree leaves files in the main checkout.

  the rule and its 7 Nov window are written in [ops/README.md](ops/README.md#run-slot).

## After a power cut

- A boot with no clean shutdown can leave a torn loose object in the shared git store, which breaks every `git fetch`, and a merge lock its dead pr:merge run held.
  ops-tick's `boot-check` beat takes both on, once per boot, on a minute inside gh-auth's first 10 minutes (`BOOT_MS` in `packages/scripts/src/ops-tick/tick.ts`), keeping the boot it finished in `ops/tick/boot-check.json`.
  It reads the boot alone (`readBootTime` in `packages/scripts/src/ops-machine/readings.ts`: macOS's `kern.boottime`, Linux's `/proc/stat` btime), never a wake, since every process from before a sleep lives on.
- First it lets go of a merge lock whose `pr` file is older than the boot, into `merge-locks/<pr>-<epoch ms>-boot`, with one line to Ops: every process of the old boot is dead, and a pid from then can name a live process now.
- Then it runs `git fsck --no-dangling` on the shared store through run-slot (3 s measured on the main checkout's store), which stops at the first torn loose object, so it runs again after each repair, 10 passes at most.
  A torn object that only a gate-owned worktree's HEAD or HEAD reflog names (`GATE_WORKTREES`, `merge-types` today) is repaired under the merge lock: the object moved into `ops/git-torn/<sha>-<epoch ms>`, the worktree's HEAD re-pointed with `git update-ref --no-deref` to the newest commit its reflog holds that reads whole, and one line to Ops.
  While a live merge holds the lock the repair waits for the next minute.
  The `invalid reflog entry` fsck then names for a moved object counts as repaired.
  fsck names a torn object two ways, both read: a `fatal: loose object <sha> ... is corrupt` stop for one a HEAD reaches, and an `error: <sha>: object corrupt or missing` line for one only a reflog names.
- Every other break gets one line to Ops' waiter queue and one Inbox alert naming the path, and the beat changes nothing there.
- A check that a live merge's lock or a failure kept unfinished through the window gets the same line and alert once the window ends, naming why, so a dropped check is never silent.
  The logic lives in `packages/scripts/src/ops-tick/boot-check.ts`; tests: `bun run test:file tests/packages/scripts/src/ops-tick/boot-check.test.ts`.

## An edit script's replacements

An edit script that writes code or text with JavaScript passes each replacement that may hold `$` through a replacer function, `s.replace(a, () => b)`, or `split(a).join(b)`, since a string replacement reads `$$`, `$&`, `` $` ``, `$'` and `$1` as patterns: `"a".replace("a", "echo $$")` gives `echo $`, and an edit script once turned `$$` into `$` in `run-slot.sh` with no error.
In the repo's TypeScript, `tests/packages/scripts/src/replace-dollar.test.ts` fails on a literal replacement holding `$$`, `` $` `` or `$'`, or `$&` after a string search, naming the file, the line and the fix.

## A zsh loop's variable names

In zsh, `path` is tied to `PATH`, so name loop variables `p` or `file`, never `path`: a loop whose variable is `path` sets `PATH` to each item in turn, so every command after it that is not a builtin fails as not found, and a check written `cmd && echo ok || echo MISSING` then reports every item missing.
