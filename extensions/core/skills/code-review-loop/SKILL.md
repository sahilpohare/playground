# code-review-loop

One reviewer session per PR scores it out of 5, round by round, until nothing but nits is left to change. Every round is a **subscription** kept by the session: each push gets a round, each finding stays open until a round sees it fixed, and each thread you opened you close. The method on two axes is core's `code-review`, loaded by name; this skill adds the score, the gate's verdict line, the rounds and the threads.

`${CLAUDE_SKILL_DIR}/scripts/state.ts` reads a PR's state from GitHub and git each time it runs, with no memory of its own, so a round never rests on what the session remembers. `<repo>` is `owner/name` (`acme/app`), `<clone>` your review worktree, `<n>` the PR and `<branch>` its branch. Every reviewer posts from the same account, so the verdicts on a PR are one history: its rounds count on across reviewers, and the newest verdict is the PR's, whoever posted it.

Your brief names the PR, the worker you report to and your worktree. A Playground review clone is `.claude/worktrees/review-<n>`: when it is absent, reuse your newest free clone, one whose PR has merged or closed and that no live reviewer holds by the roster, by `git -C "$PLAYGROUND_REPO" worktree move .claude/worktrees/review-<old> .claude/worktrees/review-<n>` first, then `git -C <clone> fetch origin pull/<n>/head` and `git -C <clone> checkout --detach FETCH_HEAD`, then the install below, since the nightly clean reads a detached clone's PR from its folder's name and trashes one left at its old, merged number; make a fresh clone only when none is free, since one writes about 115k files where a reuse wrote 3 to 53. A clone handed to the cleanup at its PR's close is still free to reuse: once moved, send the session you report to its old and new paths by SendMessage, so the cleanup drops the old path, which no longer exists, and takes the new one when that PR closes. Run its lefthook as `bun run --cwd <clone> lefthook`, since its `node_modules/.bin/lefthook` by absolute path from the main checkout is refused, and before a fixture-stack round in a moved clone, read [scripts/README.md](../../../../scripts/README.md)'s `git worktree move` line. Your worker starts you in the same step as its tester, once the head is ready (its checks green), so round 1 opens on a ready head. A work-org PR's review worktree goes in its repo's checkout under the work org's folder (`~/<org>/`), or in your scratchpad when there is none, outside the Desktop folder, which macOS privacy refused for sessions under herdr on 22 Oct ("Operation not permitted"), stalling every review there, while the clones under that folder kept working. CI is GitHub Actions' `Audit, Lint, and Build` and `test` green at the head, which run on every push to the pull request (The last 5/5). Run your checks one after the other, never in parallel in one clone: `bun run test` rebuilds `packages/*`, which a parallel `check-types` then cannot find. Your clone takes its `node_modules` from `~/.playground/ops/run-slot.sh <your session name> -- bun install --cwd <clone>`, 2 to 4 s on the warm cache (PG-1344, measured; a sibling's `node_modules` clone is the cold-cache fallback, [scripts/README.md](../../../../scripts/README.md#a-worktrees-node_modules)), started as step 1 says; the `no-unslotted-run` hook refuses an install outside run-slot. Before a fresh clone's first check, copy its `.env.example` to `.env`, set `POSTGRES_URL` (a loopback URL; nothing connects to it) and `BETTER_AUTH_SECRET` (`openssl rand -hex 32`), since `bun run test`'s package build checks both. `bun run test:file <files>` and `bun run check-types:tests` build the unbuilt packages their files import before they run, so a fresh clone runs them directly. Build one package in the clone yourself as `~/.playground/ops/run-slot.sh <your session name> -- env NODE_ENV=production SKIP_ENV_VALIDATION=true <clone>/node_modules/.bin/turbo run build --filter=<pkg> --cwd=<clone>`, since `bunx --cwd=<clone> turbo …` from the main checkout is refused. A work-org PR keeps to the **classified** rule in every comment: the verdict line and the `ReviewBot` signature are the only names a comment carries.

On a colleague's work-org PR whose review ask came to the owner, the session that posts the review turns at once to the work org's ticket skill (its folder from `playground ext which <skill>`) for what follows a review the owner was asked for.

## Each round

1. **Recover.** Read this skill's newest text from its folder in the main checkout, `$PLAYGROUND_REPO/extensions/core/skills/code-review-loop`, with the Read tool: its SKILL.md and each file under `references/` the round uses (**release** says why). That folder is the one `${CLAUDE_SKILL_DIR}` stands for in every command the round runs, `scripts/state.ts` included, since a Read leaves the variable unfilled; a skill the round loads that `playground update` named as changed is read from its own folder there the same way. Check out the round's head in `<clone>` (`git -C <clone> fetch origin <branch>`, then `git -C <clone> checkout --detach <head>`; a round that needs a fixture stack takes `git -C <clone> switch -C review-<n> <head>` instead, since the dev skill's branch rule refuses a detached HEAD), since `code-review` reviews the clone's `HEAD` either way. Run `${CLAUDE_SKILL_DIR}/scripts/state.ts pr <repo> <n>`, then read every comment, review and thread reply it lists as said since the newest verdict, and every open thread it lists, anyone's, before you write a word. On your own first round, read the PR's whole history instead (`gh pr view <n> -R <repo> --comments`), resolved threads included: the reason a thread closed is the best account of what the author already tried. Compare each one's time with the head's: a review written before the head speaks for an older commit. A PR that reads `MERGED` or `CLOSED` gets no round: tell your worker. On a dependency or CVE bump, run the work org's ticket skill's **duplicate** check (in its extension), its search and its lockfile diff, in the PR's repo first; a bump that check calls the duplicate gets no round: tell your worker. A finding another reviewer or a person made counts as open until a round sees it fixed. A lead's ruling (a comment whose first line starts `Lead ruling:`, playbook's **gate**) supersedes the FAIL it names, the newest ruling winning: count that FAIL's fault as moved once `gh api repos/<repo>/issues/<issue>` shows the issue it names exists, and as open while it does not. When `state.ts pr` prints `GraphQL spent`, it read over REST: count each thread whose resolution reads unknown as open until the reset, and, since that read prints only each comment's first line and `gh pr view` is GraphQL too, take a first round's whole history from `gh api repos/<repo>/issues/<n>/comments`, `pulls/<n>/reviews` and `pulls/<n>/comments`. At round 1, start the clone's install (the install line above) as a background task before step 2, on every PR but an outside author's, which you read without running its code (PG-1280), so its run-slot wait overlaps the reading, and wait for it to end before step 4's first check. **Done when** you read code-review-loop's SKILL.md from the main checkout this round and the round's scripts and references come from that folder, `<clone>` is at the head and you can name the head, the SHA the newest verdict scored, every open thread, every finding still open from anyone, and, for a bump, the duplicate check's result, and, at round 1 on a PR whose code you run, the clone's install is running as a background task.
2. **Place the push** (round 2 on). Run `git -C <clone> fetch origin canary`, then `${CLAUDE_SKILL_DIR}/scripts/state.ts delta <clone> origin/canary <last scored sha> <head>`. It reads `OWN` for any commit of the PR's own in the push, and otherwise compares the PR's own changed lines on each side, since a path-scoped range diff across a merge of `canary` shows `canary`'s work as the PR's; context lines and hunk positions are left out, so a conflict resolved by hand that kept both sides reads `BASE-MERGE` too. For a stacked PR whose base squash-merged into `canary` since the last scored SHA, place the push by VERIFY.md's **Read a stacked PR's own lines** instead, since `delta` reads that whole base as the PR's. `BASE-MERGE`: when the merge is not clean, read each resolution (`git -C <clone> show --remerge-diff <merge>`), check the merge's conflict resolutions and every new `run(`, `Bun.spawn` and `claude_*` query it brought in against the fixture guards, then go to step 6 with the PR's standing score; a standing 5/5 is still a **candidate** there, so it runs The last 5/5's fresh full read and check-types at the new head before it posts (on one PR, round 2 posted 5/5 at a merge head with neither). `OWN: <files>`: read the PR's own commits since the last scored SHA (`git -C <clone> log --no-merges -p <last>..<head> ^origin/canary`, since without `^origin/canary` a merged `canary`'s commits list as the PR's), and each merge commit in that range by its own resolutions (`git -C <clone> show --remerge-diff <merge>`). A `--remerge-diff` hunk in a file outside the merge's Conflicts list (`git -C <clone> merge-tree --write-tree --name-only <parents>` names the same files) is an edit made inside the merge, not a resolution: score it blocking, since pr:merge's keeps-canary gate refuses the squash when the hunk drops a line `canary` added, and name the fix its README gives, redoing the merge plainly and putting the edit in a commit of the PR's own. The case is one PR's c45138e: stale.ts merged cleanly, yet that merge changed `canary`'s `kind` line. **Done when** every own commit since the last scored SHA is read, and every merge's hunk outside its Conflicts list is scored, or the push is shown to be a base merge.
3. **Read the spec.** Gather what was asked into one file in your session's scratchpad: for a Playground PR, the issue it closes (`gh issue view <n> -R <repo>` for its `Closes #<n>`, its "Done when"), the worker's brief (ask your worker for its path when your brief does not give it) and the ask the PR body states; a row edited after the head was pushed is the spec still, with the edit named in the verdict; for a work-org PR, the org's ticket and every comment on it, since a lead's comment often holds the requirement, and its status: a PR still open against a Canceled ticket is a finding. **Done when** the file lists each "done when" item and each stated fix direction as its own line to check, each sample the ticket carries (emails, files, payloads) as its own line too, and, for a work-org PR, the ticket's status.
4. **Review on two axes.** Take each part below that this round and this diff call for, in order. **Done when** every part that applies has met its own Done when.
   - **Stacked child:** A stacked child takes [VERIFY.md](references/VERIFY.md)'s **Read a stacked PR's own lines** alone (VERIFY's `<base ref>` is the parent's branch, whatever the child's GitHub base): its fixed point, its push delta and its base after the parent lands are that section's, by the PR's state there, so the `canary` formulas in this step never read the parent's lines as the child's, and a stacked child that fails playbook's stack test (DISPATCH.md's bundles) is a blocking finding. **Done when** the fixed point you pass `code-review` is the one [VERIFY.md](references/VERIFY.md)'s **Read a stacked PR's own lines** names for its state.
   - **Agent-facing docs:** When the diff changes an agent-facing doc (a `SKILL.md` or its sibling files, `AGENTS.md` or `CLAUDE.md`, an `.agents/dashboard` rule, `scripts/README.md` or `scripts/hooks/README.md`, a `docs/<bucket>/<name>.md` page; playbook's **writing** rule), call the Skill tool with `writing-for-agents` once a session, before the first such judgement, and judge each changed one against it on Standards, a Playground docs page against `.agents/writing-docs.md` too; a PR body is not one. **Done when** every changed agent-facing doc is judged against writing-for-agents.
   - **Fresh read:** Round 1 and every 5/5 candidate (below): call the Skill tool with `code-review`, passing the fixed point (`git -C <clone> merge-base origin/canary <head>`), the spec file's path (so its issue-tracker setup does not apply) with the file's lines pasted after it, which you then give the Spec sub-agent as the spec's fetched contents when `code-review` builds its prompt, so that sub-agent holds the spec whatever files it can read, and [VERIFY.md](references/VERIFY.md)'s path for its sub-agents to check findings by; as standards sources it takes `AGENTS.md`, every `.agents/dashboard/<topic>.md` whose area the diff touches (AGENTS.md's dashboard pointers name each one's area), `scripts/README.md` and `scripts/hooks/README.md` when the diff touches spawn.sh, ops-herdr or a hook, every `SKILL.md` the diff touches or whose subject it changes, your brief's rules, and, for a diff that changes an agent-facing doc, the `SKILL.md` under the "Base directory" line your writing-for-agents load printed (with `.agents/writing-docs.md` for a Playground docs page). Its two sub-agents start with no memory of earlier rounds, which is what makes the read fresh, and VERIFY.md's **Search inside the review** bounds their searches and background tasks. Their prompts also say they leave `<clone>` as it stands, reading its files and running git's reads alone there (`diff`, `log`, `show`, `grep`), with no merge, checkout or reset there, and once they return `git -C <clone> rev-parse HEAD` still prints the head; on a moved HEAD, check out the head again and run `code-review` again, since on one PR the clone's HEAD took a merge of `canary` while they ran and both read 17 of `canary`'s files as the PR's. A Spec sub-agent that reports the spec missing or unreadable is a failed read, never a pass, though `code-review`'s own text skips the axis then: run `code-review` again with the spec's lines in the Spec sub-agent's prompt, since on one PR the Spec sub-agent called the reviewer's scratchpad spec file missing, and a round with no Spec axis reads as a pass. **Done when** every `code-review` call's Spec sub-agent prompt carried the spec's lines, a Spec read that found no spec ran again, `git -C <clone> rev-parse HEAD` printed the head after every `code-review` call, and every spec line is marked delivered, partial or missing.
   - **Other rounds:** judge the delta from step 2 yourself on the same two axes, **Spec** (the right thing: every spec line delivered, nothing unasked) and **Standards** (built well). **Done when** every spec line is marked delivered, partial or missing.
   - **Schema shape:** when the diff touches `packages/db/`, you are the schema's advisor (`db-migration`'s step 0): judge the shape on the choices that step names as hard to reverse, and score a change that is not additive as blocking until the PR names the owner's go by its Inbox `#iN`. Before you ask for a migration to be held or delayed, check what the head's code needs from it: a held migration that also adds columns leaves the restarted head without the columns its inserts and selects name (round 4). **Done when** a diff under `packages/db/` has its shape judged.
   - **Samples:** when the ticket carries samples, build your own **samples table** from the spec file's samples, one row per sample: the sample, the path that handles it end to end, and its outcome at the head, taken from running or tracing that sample through the head's code, and posted in the verdict ([COMMENTS.md](references/COMMENTS.md)); the PR body's table is the claim you check against yours. The unhandled samples are one blocking Spec finding listing their rows, unless the ticket's Status section records the split as the work org's ticket skill asks, the owner's words quoted with their link. Every round, a base-merge one included, re-runs every row at its own head. **Done when** a ticket with samples has your samples table with a row for each.
   - **Lifecycle table:** when the diff holds a long-lived connection (a socket, a pub/sub subscriber, a retrying client), ask for a lifecycle table in the PR's Evidence with one row per path: connect, a connect that fails partway, a drop, a hang after connect, reconnect and resubscribe, close, and a member who loses access, each row giving the behaviour and the test that proves it, or the reason the path cannot happen. A missing table, or a row with neither, is one blocking finding, since reviews that found one such path a round took five rounds and 80 minutes on one PR, where a sweep of every path at once closed in two. **Done when** a diff holding a long-lived connection has its lifecycle table checked row by row.
   - **Refusal table:** when the diff loosens a guard (a hook under `scripts/hooks/` that refuses a call), first check that the loosening passes the docs-path rule in playbook's [SESSIONS.md](../playbook/SESSIONS.md#spawn), a loosening that fails it being one blocking finding that names the working form, then ask from round 1 for a `canary | head` table of refusal rows in the PR's Evidence: one row for each row the PR adds to `tests/scripts/hooks/fixtures/refused-forms/` (its own source's `<n>.ts`), each bypass the review finds that canary refuses (added to the fixture in the same PR, its forms sent by [COMMENTS.md](references/COMMENTS.md)'s **A working bypass**) and each row a source file's `allowed` list names, with the reason in the PR's body; the fixture's other rows stand through `tests/scripts/hooks/refused-forms.test.ts`'s pass count at canary and at the head, cited under the table. Each row canary refuses stays refused at the head, or its source file's `allowed` list names it; the refused-forms test goes red on any other, and on any spelling of a row's path flag whose verdict differs from the row's. A missing table, or a row canary refuses that runs at the head unnamed, is one blocking finding, since two guard-loosening PRs each took 6 to 7 rounds reopening bypasses canary refused, one class a round. A diff that changes how a hook reads a reader other hooks share (`bunCall`, which `no-main-checkout.ts` exports and `no-unslotted-run.ts` and `no-extensions-write.ts` import) feeds the table's forms to every hook that imports that reader too (`git -C <clone> grep -l <reader> -- 'scripts/hooks/*.ts'`), since on one PR `no-main-checkout` read `bunCall` anew, `no-unslotted-run` kept the old premise, and a clone build ran with no slot. **Done when** a diff that loosens a guard has passed the docs-path rule or holds that finding, and has its refusal table checked row by row against canary with the refused-forms test green at the head, and every hook importing a shared reader the diff reads anew has taken the table's forms.
   - **Hook differential:** when the diff changes a hook under `scripts/hooks/`, run the `bun run hooks:differential` command the PR's Evidence names from your clone at the head; a first line `reused: <key> from <iso>, head <tree sha>, canary <sha>` is the author's run at that same head tree and canary sha, so quote it as Evidence; it runs fresh on its own when the head or base moved, and add `--fresh` only when you doubt the author's run ([scripts/README.md](../../../../scripts/README.md#bun-run-hooksdifferential) holds the key). A hook the PR adds replays against an allow-all baseline, its counts line naming that `baseline`; a hook that judges by role allows every call with no role, so its command carries `--role <role>`, or `--role session` to judge each call as the session that made it, and a role-gated hook's counts line with no `role` is a finding. **Done when** a diff that changes a hook has its differential's counts quoted, its `reused:` line with them when one showed.
   - **Verify:** Verify what every finding rests on yourself, by VERIFY.md, whichever read produced it. A claim taken from a script's usage comment rests on the code path that comment describes: read that path before you act on it, since a stale comment reads as true (spawn.sh's resume line, which said a resume opens a workspace of its own, cost another PR a round). A finding about a pointer, link or line missing at several places lists every place the read found, each as `file:line`, so one fix round closes it. **Done when** every finding is measured or marked reasoned.
   - **Round 1 greps:** In round 1, run both greps AGENTS.md's Shipping a Playground PR step 1 names: the list grep for each member the diff adds to an enumerated kind, and the changed-term grep (`git grep -l <term>` over the agent-facing and web docs) for each term whose meaning the diff changes; file every list or doc either leaves behind as one such finding, each as `file:line`, since one PR took 7 rounds when each round found one more doc still describing the old meaning. When the PR moves text out of a file, run `git grep -n <old file name>` over the whole repo too, code comments, `scripts/hooks/README.md` and `.agents/dashboard/` included, and check each hit against the moved text at the old base (`git -C <clone> show <merge base>:<old file>`), since on one PR round 1's greps stayed inside the playbook folder and missed 7 hits outside it, which cost rounds 4 and 5. **Done when** round 1's list grep ran for each kind the diff extends and its changed-term grep for each term whose meaning it changes, with each file the PR moves text out of grepped over the whole repo and each hit checked at the old base.
   - **Dependency bump:** For a dependency-bump PR, an advisory answered no-plain-fix-exactly-pinned stands only after the audit skill's rung 2 read of each root parent's newest in-range version and its dependencies (`npm view <parent> version dependencies`), since a parent's range often already carries the fix. **Done when** for a dependency bump, the parent read is done.
5. **Hand small fixes over.** Hand each small, mechanical fix to the worker as a checked patch, and keep the PR you score free of your commits: [ADR 0004](../../../../.agents/adr/0004-an-independent-reviewer-is-the-gate.md) makes the gate a reviewer independent of the code it scores, so a head holding your own commit has no independent score. Make the edit in `<clone>`, a wording you suggest in a finding included, and run the checks its files call for (`bun run docs:wrap --check` on a wrapped doc, `bun run test:file tests/packages/scripts/src/trace-count/count.test.ts` and `scripts/check-em-dashes.sh` on any doc, the test that pins the wording, `bun run test:file` on the file's mirrored test, and on each patched test file outside `CLOCK_EXEMPT` (`packages/scripts/src/clock-exempt.ts`) one more run under `CLOCK_AHEAD_DAYS=30`, since a file's mtime and a child process stay on the real clock while the test's own clock moves, and a file the run names as left out ran nothing, a no-op rather than a pass), since a reviewer's own wording was wrong in 5 of 218 rounds in one day, each costing the PR a round, and a patch citing issue numbers once bounced its worker's commit at trace-count. When the patch edits a promoted skill's `SKILL.md`, grep each changed term over the skill's docs page (`docs/playground/<name>.md`) and every README that lists it (`git -C <clone> grep -l '<name>/SKILL.md' -- '*README.md'`), and patch every hit, since a patch that left a docs page describing the old wording cost one PR a round. Then save `git -C <clone> diff > <scratch>/fix.patch`, restore the clone with `git -C <clone> checkout -- .`, check the patch applies with `git -C <clone> apply --check <scratch>/fix.patch`, and post the saved `fix.patch` inline as a `diff` block, pasted whole and unedited with every context line kept so `git apply` takes the block as it stands, or the wording, with those results in the verdict, which step 8's link carries to the worker, since a restart clears `/tmp` and with it a patch named by its path alone; the worker applies a blocking or should-fix patch word for word as a commit of its own on the PR, which your next round scores like any other push, and a nit patch as playbook's SESSIONS.md, Fix pushes and nits sorts it. A patch only rewords, renames or deletes; anything that adds behaviour or rule text goes back to the worker as a finding. **Done when** each finding is either written up for the worker or handed over as a checked patch, its checks' results posted with it, and the head holds no commit of yours.
6. **Score** the PR, not the delta: a faultless push leaves open findings open, so the score stays at the lower mark until a round sees them closed.

   | Score | Means                                                                     |
   | ----- | ------------------------------------------------------------------------- |
   | 5     | Nothing left you would change but nits, which are listed. Merge as it is. |
   | 4     | Good; merge after small fixes. Findings are improvements, not defects.    |
   | 3     | Competent work with a real defect to fix first. The usual first score.    |
   | 2     | A core claim, the approach, or the fit to the spec is wrong.              |
   | 1     | Should not merge.                                                         |

   Any blocking finding caps the score at 3, and any should-fix finding left open at 4. In a work-org PR, scope beyond its ticket and the answers of the people its ticket skill names is a should-fix, never an improvement (`.agents/decisions.md`). A finding against a rule written in the code (a ratchet, a check whose rule says it never rises) stays blocking when your brief lists it as agreed, unless that agreement quotes the rule's owner. A round left with only nits is a 5/5 candidate (The last 5/5), its nits listed in the verdict, or handed over as your step 5 patch, which the worker keeps or drops by playbook's SESSIONS.md, Fix pushes and nits (on a colleague's work-org PR, the nits stay in the verdict for its author). What a worker's push carries is that section's too; a head at 5/5 with green checks merges as it stands, since a push after a 5/5 is a new head that needs a fresh full read. A **trust-widening nit**, one that widens a permission, a setting (`enableAllProjectMcpServers`) or a guard's reach if a rare event happens, goes first to your worker's lead (the Builder for a factory worker) by `SendMessage`, naming the event and what it widens, and the 5/5 waits for the lead's ruling: a must-fix ruling makes it a should-fix finding, and a nit ruling joins the verdict's nits beside the ruling, since on one PR the lead ruled such a nit must-fix about 25 s after the PR merged on its 5/5. A nit gets no tester or local CI round on the PR it was found on. A PR body with no `test:skills` result in it is a nit, since GitHub Actions runs the suite at the head. Before scoring, ask what can be removed (YAGNI): a speculative option, layer, setting or dependency beyond the spec's Done when is a should-fix. So is a PR body, Playground's or the work org's, that is not the [pr](../pr/SKILL.md) skill's template (a `## TL;DR` on top, Summary, Evidence and Merge Danger, `## Links` last), or whose TL;DR speaks in jargon rather than what the owner sees. The template itself is settled by the owner: no finding, nit or suggestion targets `extensions/core/skills/pr/SKILL.md`'s wording, sections or order, and none caps the score; a review checks only that the file is upstream's plus its TL;DR and Links blocks, as its drift test holds, and that a body fills the template. So is a changed agent-facing doc that writing-for-agents would change: a step with no completion criterion, a prohibition where the positive fits, one meaning written in two places, or sprawl that disclosure would cure. Score from the findings, never from the effort shown: a brilliant write-up with one real defect is a 3, and no nit is made up to justify a lower number. A lower score after an earlier 5/5 at the same head is posted as it is: the newest verdict is the one `bun run pr:merge` reads, which is the point. **Done when** each finding carries its axis and its weight (blocking, should-fix, nit), each trust-widening nit carries its lead's ruling, and the score follows from them.

7. **Post** the verdict comment and the inline review, then close the threads the head settles, all by [COMMENTS.md](references/COMMENTS.md). Right before the verdict posts, read the head's checks again by VERIFY.md's **Read the head's own checks**, since a check still pending at your earlier read can go red while you review: each check red there is a blocking finding, with its job link and its failing test or error line, and step 6 scores again with it before anything posts (on a work-org PR a verdict posted on checks read while pending, and `frontend-build` had gone red at that head). The post runs behind `${CLAUDE_SKILL_DIR}/scripts/state.ts fresh <repo> <n> <read-at> <digest>`, the two values on the `read:` line of your last `state.ts pr`, chained as COMMENTS.md gives it: it exits 1, naming each change, when the body was edited or a comment, thread reply or review came after that read, so a before shot or an Evidence edit made during the round is seen; post the verdict first, then the inline review, since the inline review's own comments would trip it. On `CHANGED`, read the body and each comment it names, drop each finding they now answer and score again for the rest (step 6), run `state.ts pr` again for a new `read:` line, then post (one PR's round raised two findings the author had answered minutes before the verdict). **Done when** the head's checks were read again right before the verdict posted, every check red there is a finding in it, the verdict posted behind a `fresh` that printed `FRESH`, `state.ts pr` shows your new verdict at the head, and its open threads are exactly the findings still open (over REST, where every thread reads unknown, that check waits for the reset, as COMMENTS.md says).
8. **Report and wait.** Send your worker the score, the counts and the verdict's link, in 5 lines at most, by name, or, when that send fails, to the `uds:` address its newest message came from (playbook's SESSIONS.md, Message a session). ## The recovery scan

A lead's sweep runs `extensions/core/skills/code-review-loop/scripts/state.ts scan <owner/name>` with the factory's repo (`factory.repo`) from the Playground checkout (`$PLAYGROUND_REPO`), since the sweep runs outside this skill. It asks GitHub which open PRs have a head no verdict scored, with no cursor, no seen-list and no cache in the path, so it catches the PR whose reviewer closed, crashed or was never spawned. Each row is `UNREVIEWED`, `STALE <s>/5 at <sha7>` or `SCORED <s>/5`, with its holder in brackets: the agents holding the PR (the roster's, by their `pr`, and each live worker an item of the Planner's `bundles/plan.json` gives it as its `pr`, so a worker on a lane of several PRs holds each), else `outside author <login>: the builder triages (a colleague's: the dispatcher decides per the org's channel triage; another's app PR: read-only review then the gate; skills/factory: closed)` for a PR another account opened, which the Builder triages without asking, sending the dispatcher one line per PR; else `no agent; parked in plan.json` when a `plan.json` item names it with no live worker, or `no agent; parked in <plans file>` when a plans file names it, else `no agent, in no plan: lost`. A row not scored at its head, held by a worker, whose PR has no live reviewer in `ListAgents` gets one, spawned by that worker. A parked row stays as its plan says. A lost row is dispatched, or put up the chain before its PR is closed. **Done when** every unscored row held by a worker has a live reviewer, and the `RESULT` line's lost count is 0 or each lost row is dispatched or put up the chain.
