# pr:merge and pr:train

A Playground PR reaches `canary` only through `bun run pr:merge <n>`, or merge-on-ready (`bun run pr:train ready`), which runs pr:merge on the first gated PR in queue order, once it is ready at 5/5 with GitHub's checks green at its head, for a diff under `web/next/` its tester's PASS there, and for an installer or first-run diff the new-user gate's PASS there.
This file holds the gates, the merge lock and the merge queue's readers.
Every gh call either makes goes through `runGh` in `merge.ts`, which skips gh and answers `gh unreachable: <reason>` while ops-tick's gh sign-in probe reads failed, so a broken gh is never flooded ([LIFECYCLE.md](../../../../extensions/core/skills/playbook/LIFECYCLE.md)'s ops-tick beats).

## Gates

Every gate judges the PR's head as GitHub names it (`headRefOid`), which pr:merge and the train's forecast fetch from its pull ref, `refs/pull/<n>/head`, else, while GitHub has not made that ref yet, from its branch (`headRefName`), refusing a branch whose tip is another commit (`fetchHead` in `merge.ts`).

A draft left green reaches `canary` too: when the owner's draft passes every gate but ready, pr:merge marks it ready (`gh pr ready`) just before its squash, merge-on-ready takes it, `--explain` names it, and an outside author's draft is never touched (`marksReady` in `gates.ts`).
pr:merge refuses a PR the repo's owner did not open unless `--outside-author <login>` names its author (an outside PR's code runs here, so it merges only on a lead's go, after its read-only review), refuses a PR `~/.playground/ops/report/held-prs.json` lists at the gates or just before the merge call, naming its reason (`PLAYGROUND_HELD_PRS` moves it, as the tests do; a `"*"` line until it lapses (Holds and rulings), or a file that does not read, holds every PR), and refuses unless:

- `code`: the checkout pr:merge runs from holds `origin/canary`'s gate code, since a hand merge runs its own checkout's gates while the train runs from a worktree reset to `origin/canary` (a hand merge from a checkout behind `canary` once skipped a tester gate the train held its PR on).
  After the fetch, `git diff --name-only <canary> -- <GATE_CODE>` against the working tree, uncommitted edits included, must name no file under `packages/scripts/src/pr-merge/`, no `packages/config/src/verdicts.ts` and no `packages/scripts/src/new-user-gate/paths.ts` (`gateCodeOf()` in `merge.ts`, `GATE_CODE` in `gates.ts`); else it refuses, naming each file, and `--explain` shows the same ✗.
  A PR's own worktree or review clone reads ✗ here whenever its gate code differs from `canary`'s, whether the PR changes a gate or its branch predates one, so that ✗ is the checkout's: its worker and reviewer read every other gate there, the whole verdict comes from a checkout on `origin/canary`, and merge-on-ready lands the PR.
- `parent`: every PR the body says it is stacked on, each `Stacked on #N` anywhere in the body (playbook DISPATCH.md's stack line, in any case, a list such as `Stacked on #N and #M` included), reads `MERGED`, since a review scores a stacked PR's own lines alone and its squash would land an unmerged parent's lines unreviewed (`parentGate` in `gates.ts`, each state read by `factsOf`).
  An open parent refuses, naming it; a parent closed without merging refuses until the body loses its `Stacked on #N` line, once its lines land another way; a state gh cannot read refuses, so the gate fails closed.
  A body with no such line meets no `parent` gate.
- `up to date`: the head holds everything on `canary`, or merges with it clean; a conflict waits for a merge of `canary`, whose new head then needs its own checks and 5/5, and its own tester's or new-user gate's PASS where its diff calls for one.
- `ci`: the newest run of every GitHub check on the head, by workflow and name, has finished and passed, since a rerun or a close and reopen leaves the older runs listed; `Audit, Lint, and Build` and `test` (`REQUIRED_CHECKS` in `gates.ts`) are among them, and on factory.repo (the checkout's origin when unset) a GitGuardian check too, since a head GitGuardian never started on ran no secret scan.
  A required check missing while every job of its workflow's run passed is GitHub's: it ended that run without creating the job and concluded it `failure`, as run 42670675952 did with all 20 jobs green, so `ci` names the run and its step, `gh run rerun <run id>`.
  That rerun tests the same merge, which suits this shape alone, since the run's code was green; a red check's step stays a fix or a merge of `canary`.
- `body`: the PR body is the PR template, its TL;DR holds no `Outcome:` label line, and its Evidence section names each changed `*.md` path (a `SKILL.md` included) by its full repo-relative path, as `.agents/shipping.md` asks, and holds a line that opens with `A/B:` (a bullet, bold or plain, outside a code fence), the PR's measured comparison: A and B against the bar, or `A/B: No runtime metric` and the check that stands in, and holds no `TBD`, in any case, outside a code fence or inline code (`bodyRefusal()` in `body.ts`, which names why it refuses, each doc left out and the TBD line; `abLine()` reads the A/B line and `tbdLine()` the TBD one).
  Its prose, outside code fences and inline code (a code span kept to its line), holds no unfilled placeholder: no `<...>` of the template, read from `extensions/core/skills/pr/SKILL.md` at the head (`templatePlaceholders()`), and no bare all-caps token with an underscore (`SUITE_LINE`) that `git grep -w` finds in no file at the head (`unfoundTokens()` in `merge.ts`), so a real identifier such as `CLOCK_EXEMPT` passes, and the refusal names each token.
  The grep leaves out the gate's own folders (`GATE_OWN`), whose code, docs and tests name sample tokens that would else read as found, and a template the head cannot show, or one holding no placeholder, stops the run with why, so the check fails closed.
  The changed paths are the PR's files from the one paginated `pulls/<n>/files` read `factsOf` makes, a renamed file by both its paths, so Checks, `pr:merge`, merge-on-ready and the train judge the same list.
- `review`: the newest `## ReviewBot · round <n>: <s>/5 at <sha7>` on the head reads 5/5.
- `checks`: a PR changing a check that judges it merges only once that 5/5 names each such path in a line of its own, `Reviewed check change: <path>`, since a change can never edit the check that judges it unseen (`checksGate` in `gates.ts`).
  A check (`CHECK_CODE`) is a path under `.github/actions/` or `.github/workflows/`, a gate code path (`GATE_CODE`: `packages/config/src/verdicts.ts`, `packages/scripts/src/new-user-gate/paths.ts` and `packages/scripts/src/pr-merge`), or the refused-forms harness (`tests/scripts/hooks/fixtures/refused-forms.ts`, `tests/scripts/hooks/refused-forms.test.ts`), any change to which counts.
  So is a file under `tests/scripts/hooks/fixtures/refused-forms/` the diff deletes a line from or renames away, read from the same `pulls/<n>/files` read as its deletion count, so an edited row counts as removed.
  A path the verdict names outside the diff counts for nothing, and the refusal names each path still unnamed; a PR changing none passes with `the PR changes no check that judges it`.
- `tester`: on a diff with a file under `web/next/`, the newest `## TesterBot · <PASS|FAIL> at <sha7>` on the head reads PASS, since a UI change lands only once its tester has driven it (`testerGate` in `gates.ts`; a UI PR once merged on ready while its tester's drive was still open).
  No verdict at the head refuses, naming the line it waits for and the next move, spawn or resume the PR's tester; a FAIL, or a PASS at an older head, refuses too, and a diff with no `web/next/` file meets no `tester` gate.
- `new-user`: on an installer or first-run diff, one with a file `NEW_USER_PATHS` covers (`packages/scripts/src/new-user-gate/paths.ts`: the installer, first run's trust and setup, the first start and the gate itself, `scripts/spawn.sh` whole, since a gate run takes 65 to 121 s, well under the 10 minutes that would call for matching only its first-start block), the newest `## NewUserGate · <PASS|FAIL|INCONCLUSIVE> at <sha7>` on the head reads PASS (`newUserGate` in `gates.ts`), since a broken `curl | bash` once showed only at a ship's gate run.
  `bun run gate:new-user <head> --pr <n>`, run through `~/.playground/ops/run-slot.sh`, posts that line from a file with `gh pr comment --body-file`: FAIL on a failed step or a run cut short, INCONCLUSIVE when a step was (it reads this machine, not the build), else PASS, then the count and each step that did not pass.
  An INCONCLUSIVE refuses like a FAIL, its reason printed; no verdict at the head refuses, naming the matched files and that run; a diff matching no path meets no `new-user` gate.
- `types`: last, inside the merge lock once every other gate passes, the tree the squash makes type-checks (`types.ts`), since a head's own checks typed it alone and a clean textual merge can still call an API `canary` changed.
  It skips when the head already holds `canary`'s tip (`git merge-base --is-ancestor`), whose own checks typed that very tree.
  Else it checks the `git merge-tree --write-tree` tree out detached in `.claude/worktrees/merge-types`, the one worktree every merge reuses and keeps however it ends, since cloning and removing a whole `node_modules` (about 114k files) on each merge drove the load to 93 on 2 Nov.
  It forces the checkout to the tree and removes every untracked and ignored file but `node_modules` (`git clean -ffdx -e node_modules`), so nothing the last check left reads into this one.
  `node_modules` takes a clone of the caller's when the worktree has none ([scripts/README.md](../../../../scripts/README.md#a-worktrees-node_modules)), then `bun install --force` in place of that section's plain install first, since a fresh copy that printed any error needs the forced one.
  A kept `node_modules` takes a plain `bun install` when `bun.lock`, `bunfig.toml`, a `package.json` or a file under `patches/` differs from its last install, as `node_modules/.merge-types-deps` records them; an install removes that record first and writes it once it exits 0, so a retry after a clone or install that never finished takes the plain install too, which repairs a partial copy (measured), and a forced one there would rewrite every package (27s measured, against 0.2s plain).
  It then runs CI's own type steps there, each through `~/.playground/ops/run-slot.sh` as `ops-merge-train`, whose class 0 skips the queue and whose quick step starts at once, past the quick slot's race, since every step runs inside the merge lock (bare under a run that already holds a slot, or with no run-slot): `turbo run check-types --filter='...[<canary>]' --filter=@packages/scripts` (the second filter as CI has it, for the reason turbo.json's `@packages/scripts#check-types` gives), the build and data-table metrics `check-types:tests` reads, then `check-types:tests`; its pass names each step's seconds.
  When the PR's diff from `canary` touches `scripts/hooks/` or `packages/`, whose files a hook imports, `hooks-bundle.ts --check` runs first, after the install, since a head branched before another PR rebuilt a bundle passes its own checks while the squash writes that bundle beside the source this PR changed (3 Nov: a shell.ts change merged after a rebuild of no-raw-delete.js it predated, and canary went red).
  The pre-push `hooks-bundle` job runs the same check earlier, on the head merged with the local `origin/canary` (`--check --merged`, [scripts/hooks/README.md](../../../../scripts/hooks/README.md)), and this gate stays the one that reads the fresh `canary`.
  A type error refuses with the first errors and the fix (merge `canary` in, fix it, and the new head needs its checks, a 5/5 and each PASS its diff calls for), and a stale bundle with the files `--check` names and its fix (merge `canary` in plainly, run `bun run hooks:bundle` and commit the rebuild on its own, then checks, a 5/5 and each PASS its diff calls for); either is kept beside the lock (`merge-types/<head>-<canary>`), so merge-on-ready's next cycle refuses the same pair at once; a run it cannot finish in 600s (`TYPES_BUDGET_MS`, which every gate in one `pr:train ready` call shares, so the call ends inside the merge train's 900s), counting each step's wait for a CPU slot as well as its run, or a step that fails another way refuses, naming it, and runs again on the next try.
  `--explain` names whether it would run or skip, and why, and runs no type check.

Every verdict is read from the comments of the account that owns `factory.repo` alone (`packages/config/src/verdicts.ts` parses them): the reviewer's `## ReviewBot` line, which the `review` gate reads, and the tester's `## TesterBot · <PASS|FAIL> at <sha7>` line, which the `tester` gate reads on a `web/next/` diff and the Dashboard shows, and the new-user gate's `## NewUserGate · <PASS|FAIL|INCONCLUSIVE> at <sha7>` line, which the `new-user` gate reads.
`--explain` prints each gate and what it found.
suite.sh's `audit` fails only on an advisory the head adds over its merge base with `canary`.
It also refuses a head holding a merge of `canary` that dropped a line its `canary` side added, in a file git merges without a conflict, which git's own merge of its two parents (`git merge-tree --write-tree`) keeps, `canary` still holds and the squash onto `canary` lacks (`keeps canary`, `lost.ts`), naming each file and merge:
a merge with `-s ours` leaves exactly that while `canary` reads as merged in.
A read it cannot finish refuses too.
lefthook's pre-push script `keeps-canary` (`.lefthook/pre-push/keeps-canary.sh`, which runs `prepush.ts`) runs the same check before the push lands, a review round sooner: on a push whose range holds a merge, it reads the squash onto `origin/canary` as fetched with `lostLines` and refuses in this gate's words, from local git alone, while a head that conflicts with `canary` passes it, since this gate names the conflict.
A blank line, a move (its text added elsewhere in the merge's diff) and a rewrite (a line its hunk adds is 80% alike) pass.
A line a merge of `canary` dropped clears once the squash holds it again or `canary` drops it too, so it stays lost after a new merge of `canary` and after a restore that a later own commit replaces: redo that merge plainly and re-apply the change in a commit of the PR's own, or keep the line.
When every lost line sits under `scripts/hooks/bundled/`, the refusal names its cause, bundles rebuilt inside the merge, and that redo: merge `canary` plainly, commit the merge with `canary`'s bundles as they are, then run `bun run hooks:bundle` and commit the rebuild on its own (`hooks:bundle` refuses to write while a merge is in progress).
After that reset, `bun run hooks:merge-canary` makes that merge and rebuild, two commits, from a clean tree (`scripts/hooks/README.md`).

## Holds and rulings

A hold is a line in the `held` object of `~/.playground/ops/report/held-prs.json`, `"<owner>/<name>#<n>": "<reason>"`, which Ops writes the moment a lead sends `hold <owner>/<name>#<n>: <reason>` and removes on the lead's word; pr:merge and merge-on-ready refuse a listed PR, naming the reason: each reads the file at the gates and again inside the merge lock, after the types gate and just before the merge call, so a hold written while the type check runs still stops the merge.
One `"*": "<reason>"` line holds every PR at once, as a ship's merge hold does, while a PR's own line keeps its own reason.
A ship writes it with `bun run ship:freeze <version>` (`startFreeze` in `held.ts`), with the time in the file's `since` object, and removes it with `bun run ship:freeze --end` (`endFreeze`), at the points the release skill names, from its step 1 to its step 4's tag ([SKILL.md](../../../../skills/zerostarter/release/SKILL.md#1-pin-the-content)).
`bun run ship:freeze status` prints the `"*"` line, its `since` (or focus's `until`) and whether it has lapsed, or that none is set, and writes nothing (`freezeStatus`); any other word that is not a version (`vX.Y.Z`) prints the usage and writes nothing, since a stray word written as the version would hold every PR.
A freeze's own `"*"` line (its reason ends `ships: canary is frozen until its tag lands`) lapses 4 hours after that time (`FREEZE_LAPSE_MS`), so a ship that stopped without its `--end` holds no PR for long.
A `"*"` line Ops wrote by hand never lapses, even beside a time an earlier freeze left, and `ship:freeze <version>` and `--end` both leave it for Ops to remove; a PR's own line never lapses either.
`playground focus on` writes focus's own `"*"` line (its reason ends `has focus: every merge waits until focus ends`, `startFocus`), with the focus end in the file's `until` object, at which it lapses; `playground focus off` removes it (`endFocus`).
Focus keeps a ship's freeze or a hand line it finds, and a ship's freeze writes over focus's line, since the ship's tag waits on it.
A lead that overrules a reviewer's FAIL sends that reviewer the ruling by `SendMessage`, in the ruling shape: `ReviewBot round <r> at <sha7> overruled: <evidence>; the fault moves to #<issue>`, with that issue filed first, since a reviewer reads every PR comment as data, whoever posted it.
A ruling is the lead's own word, so it takes this shape, and the **override** shape stays for a lead relaying the owner's words that bend a rule; pr:merge reads no ruling, so the merge still waits for a fresh verdict at the head, or the Builder's merge by hand.
A red check that `canary` caused needs a fresh run once `canary`'s fix lands: merge `canary` into the PR, since `gh run rerun` reuses the run's original merge commit, which holds the red `canary`.
An outside author's PR goes to the Builder, who gives its go only after a read-only review of its diff.

## ship:merge

`bun run ship:merge <n>` is the ship skill's step 3, the one merge into `main` (`ship-merge.ts`): it merges ship PR `<n>` with a merge commit, `--match-head-commit` at the head it read, and refuses, naming each reason (`shipRefusals`), unless:

- `pr`: the PR is open, into `main`;
- `gate`: the body holds the new-user gate's PASS line for the head on a line of its own, and no FAIL line for it; the gate prints that line last (`resultLine` in `new-user-gate/cli.ts`, its words from `gateLine` in `ship-lines.ts`), PASS only for a run that reached its last step with none reading FAIL, an INCONCLUSIVE step included, since that reads this Mac, not the build.
  In the PASS line's place the body may hold its waiver, `New-user gate at <sha>: waived by Inbox <id>` (`waiverLine`, the id a uuid or `#iN`), which `ship:merge` reads through `playground ask get`, the live Dashboard's Inbox, and passes only for a decision from the dispatcher (its `sessions.names` name) reading `approved`, which only the owner's own answer sets (the agent sign-in's is refused off a fixture, `refuseAgentOffFixture`), approved by Approve on a single-question decision, and whose title or text names the next version (`waiverRefusals`).
  The row that Approve picked, read by `rowOfAnswer` (`@packages/config/inbox`), must read `Ship everything now, skip the new-user check this once` word for word once trimmed (`WAIVER_LABEL` in `ship-lines.ts`), so the dispatcher offers that label verbatim as a waiver decision's row, since a pattern over the words let a negation through; a decision with no row its poster wrote (the default `Approve`, or a typed preview) refuses. A FAIL line refuses beside a waiver too;
- `rehearsal`: the body holds the invitee rehearsal's line for the head (`rehearsalLine`), PASS or `not needed`;
- `ci`: `Audit, Lint, and Build` and `test` (`REQUIRED_CHECKS`) are each green at the head by their newest run (`ciGate`), so a suite still running or red refuses;
- `freeze`: the `"*"` line holds and is the ship's own freeze for the next version, the latest tag's patch plus one (`freezeLine` in `held.ts`, `nextVersion`), so a lapsed freeze, another version's, focus's or one Ops wrote by hand refuses.

It takes no merge lock and runs no pr:merge gate, since a ship PR merges `canary` into `main` while the freeze holds every PR into `canary`.
`bun run ship:approve-held <n>` approves ship PR `<n>`'s held CI runs at its head (`packages/scripts/src/ship/approve-held.ts`, behind the `ship` prebuild target), the `pull_request` runs the bot's draft leaves at conclusion `action_required`, and prints each run it approved or `none held`, so `ci` can read them.

## The merge lock

Only one merge into `canary` runs at a time: pr:merge takes the factory's merge lock (`mkdir ~/.playground/merge.lock`, its PR number inside; `PLAYGROUND_MERGE_LOCK_DIR` moves it, as the tests do), reads every gate and `canary` inside it, and lets it go into `merge-locks/<pr>-<epoch ms>-<random>` however it ends, a refusal included,
and only while the lock still names its PR; a lock another merge holds refuses, naming that PR.
A SIGHUP, SIGINT or SIGTERM releases it too (`stop.ts`, whose cleanups run newest first): pr:merge ends the types gate's running step and waits for it, keeping its worktree, then moves the lock into `merge-locks/<pr>-<epoch ms>-<signal>`, again only while it names its PR, and exits 128 plus the signal's number, so a run stopped by its own handle never leaves the lock held, and no next merge checks out into the shared worktree under a step still running there.
A signal that comes once the squash has begun waits for it to settle, merged or failed, before the lock goes, since the spawned `gh pr merge` would carry on past the exit; the run then posts no merge comment and ends no sessions, whatever the squash did, and a second signal exits at once.
With `REDIS_URL` set, the lock's holder is also a Redis key with a time to live (`playground:merge.lock`, `takeLock` in `merge.ts`, through `@packages/redis`), renewed while pr:merge runs, and the folder is marked with that key and its pid, so a merge that crashed leaves a lock the next merge takes over once its key lapses;
a merge that cannot reach Redis keeps to the folder alone and so is refused by any holder.
A lock taken before the machine's last boot, which a power cut can leave, is let go into `merge-locks/<pr>-<epoch ms>-boot` by ops-tick's boot check, and that check takes the lock as `boot-check` while it repairs the gate's worktree ([scripts/README.md](../../../../scripts/README.md#after-a-power-cut)).
`bun run lock take|renew|free` gives a shell script the same Redis lock (exit 3: no Redis, keep the script's own lock file).
It squash-merges with `--match-head-commit <head>` and `--body` set to the PR body less every line opening `Co-authored-by:`, in any case, since AGENTS.md's Commits rule keeps that trailer out of `canary` and GitHub's own squash body copies it from the PR's commits, tries once more on a GitHub 5xx, checks the PR reads `MERGED`, prints the merge SHA and, after letting the lock go, leaves its merge comment.
Then it ends the PR's worker, reviewer and tester (`scripts/ops/optimizer/auto_end.ts`, the factory's SESSIONS.md End) and cleans each worktree an ended one used, each line to its lead; a failure there is printed and never undoes the merge.
A PR labelled `ship-now` (the factory's **release** rule) whose title opens `fix(`, or whose Links holds a line opening `Owner ask:` with an Inbox `#i` id, a `PG-<n>` issue or the owner's quoted words (`ownerAsk` in `body.ts`), also queues Ops one line through `scripts/ops/notify.sh` as `ops-ship`, the line `shipNowLine` builds, which reaches Ops tagged `[ops-ship]`; a labelled PR with neither queues none and prints the rule's line instead.
The label and title ride the PR view the gates already read, and a failed send is printed and never undoes the merge.
`--explain` takes no lock.
Like `bun run verify`, pr:merge and pr:train first build the workspace packages they import when a `dist` is missing, is older than a file under its package's `src` while no stack runs in this worktree, or lacks a name their sources import from it, those reached through a relative import outside their folder included (`packages/scripts/src/verify/prebuild.ts pr-merge`), so either runs from a fresh worktree;
in the factory's main checkout (`$PLAYGROUND_REPO`), which builds only `packages/*` after a pull, the prebuild stops instead, verify's, `bun run dev`'s, `bun run ask`'s, `bun run thread`'s, `test:file`'s and `check-types:tests`' too, and says to run from your own worktree.
On every run, built or not, pr:merge and pr:train also stop on a worktree whose install predates its `bun.lock`, a workspace package's dependency linked neither in its own `node_modules` nor the root's (`staleInstall`, through `prebuildStep`), naming the `bun install --ignore-scripts` that fixes it, since a build would otherwise stop on `tsdown: command not found` and a run on `Cannot find module` (2 Nov, after a canary merge made `packages/settings` depend on `@packages/safe-delete`).

## When canary moves

A PR behind `canary` that merges with it clean merges on its own head's checks, 5/5 and each PASS its diff calls for once the `types` gate's check of the merged tree passes (its type check, and its bundles step for a PR touching `scripts/hooks/` or `packages/`), so several gated PRs merge back to back with no new GitHub run.
When its head conflicts with `canary`, merge `canary` in and resolve it; the new head then needs GitHub's checks and a 5/5 of its own, and its own tester's or new-user gate's PASS where its diff calls for one.
A refusal `--explain` shows to be wrong goes to the Builder, who alone may merge that PR by hand with `gh pr merge <n> --squash --body-file <file> --match-head-commit <head>`, `<file>` holding the body pr:merge would pass (above), the one hand merge the no-protected-push hook passes ([scripts/hooks/README.md](../../../../scripts/hooks/README.md#no-protected-push)), on an override in the factory's **override** shape, and has pr:merge fixed.

## The merge queue

`bun run pr:train` (`train.ts` beside it; `--help` gives each command) reads the merge queue, `merge-queue.json` beside the merge lock (`PLAYGROUND_MERGE_QUEUE` moves it, as the tests do), which the Builder keeps by playbook's SWEEP.md (step 4): the owner's open PRs in its order, then any other by number; an outside author's PR never merges on ready.
`ready` is merge-on-ready (`ready.ts`, which the merge-train ops job runs every cycle): the first PR, in that order, whose every gate passes at its head merges at once through pr:merge; one merge a call.
Each call first writes every PR it read, with the gates it fails at its head, to `<data>/ops/merge-train/gates.json` (`gates-file.ts`, a temp file moved over it), which the Dashboard's Ready and Gated states read (`.agents/dashboard/dashboard.md`).
A PR whose facts cannot be read (any read `factsOf` makes throws, such as a `gh` read on a rate limit or a failed fetch of its head) is held as `not gated: facts unreadable (<error>)` (`gatedOf` in `train.ts`), so the pass goes on to the next PR in order rather than ending.
`pr:train ready` prints each such PR on stderr as `✗ #<n> not gated: facts unreadable (<error>)`, and exits 1 when one was unreadable and nothing merged, so the merge train's log, which keeps a failing run, keeps the error.
`forecast` merges each open PR, gated or not and drafts included, onto `canary` and the PRs ahead of it in the queue, as GitHub's squash merge will, and prints each predicted conflict with its files and the PR it comes from, so a worker rebases onto the PR ahead before its next review round rather than after that PR lands; it writes nothing.
