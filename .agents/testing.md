# Testing

## The sandbox

A bare `bun test` from the repo root stops at `tests/require-sandbox.ts`, which `bunfig.toml` preloads, since only `test-sandbox.ts` gives a test a scratch home in place of the real one; bun reads `bunfig.toml` from the folder it runs in, so a run from a subfolder goes unguarded.
That sandbox (`packages/scripts/src/sandbox.ts`) also sets `TZ=UTC`, so a test's children read one zone on the Mac and the runner box; a test of code that reads local time gives its child its own `TZ`.
It takes the caller's env through `SANDBOX_KEYS` alone (`boxEnv`, `packages/scripts/src/box-env.ts`), since a variable naming live state by an absolute path (`PORTLESS_STATE_DIR` once let a scratch-HOME child stop the live proxy) survives a new HOME.
A test that gives its own child a scratch HOME builds that env with `scratchEnv` (`tests/scratch-env.ts`), which keeps the sandbox's variables; `tests/scratch-home-env.test.ts` fails on a spread of `process.env`, a rest or a filtered copy of it included, beside a HOME of its own.
It sets `PLAYGROUND_PROC` to a missing folder, so a machine reading a test leaves to Linux's `/proc` (`packages/scripts/src/ops-machine/readings.ts`, spawn.sh's and run-slot.sh's gates) reads nothing on GitHub's Linux runner rather than its real load;
a test of a Linux reading points it at recorded text from `tests/scripts/fixtures/proc.ts`, whose `sys` folder run-slot.sh reads as `/sys`, and a child whose env it builds whole passes `TEST_SANDBOX_HOME` with it, since the readings take `PLAYGROUND_PROC` under that marker alone.
It sets `TMPDIR` to the scratch folder's short `t` folder too, so every `mkdtemp(tmpdir())` folder a test or its child makes goes with the scratch when the run ends, rather than staying in the caller's temp folder (24,008 such entries once, issue 1306).
It keeps uv's Pythons and cache the real home's (`UV_PYTHON_INSTALL_DIR` and `UV_CACHE_DIR`, read before it swaps HOME), so a child's `uv run --python 3.13` finds its Python in place of downloading one.
It also puts a fake `claude`, `gh`, `herdr`, `launchctl`, `loginctl`, `portless` and `systemctl` first on PATH, each exiting 99 with a line naming the sandbox, so no test starts a session, reaches GitHub, closes a live herdr pane or starts or stops a live ops job or the live proxy; a test that needs one's output puts its own fake ahead of the sandbox's on PATH.
Its `PORTLESS_STATE_DIR`, `XDG_RUNTIME_DIR`, `HERDR_CONFIG_PATH` and `HERDR_SOCKET_PATH` name folders in the scratch, since a test run once reached the user's live systemd manager and stopped four running ops jobs.
The scratch state folder keeps portless's state files apart from the live ones, but a real stop of portless's proxy still finds a proxy by its port (1355 when no port is given) and signals it, so the scan below guards portless on macOS, and the pid view below on Linux.
On Linux each pass and each `test:skills` step runs under `bwrap` (`wrap` in `packages/scripts/src/sandbox.ts`), since a scratch HOME hides nothing a test names by its full path.
Its pid view of its own leaves a test no live process to find or signal, so portless's stop finds no proxy's pid, and its `sudo` fallback reaches the stand-in.
It mounts an empty folder over each live one that exists: `/run/user/<uid>`, `~/.claude`, `~/.config/herdr`, `~/.portless` and the data folder, `~/.playground` with the factory's herdr sockets.
It binds `~/.ssh` read-only, and binds over `/usr/bin/pkexec` and `/usr/bin/sudo` a stand-in that exits 99 naming the sandbox.
The host network stays, since the Docker tests reach their containers on 127.0.0.1, so a test still reaches a live server by its port, and a live container by its name through the Docker socket.
A Linux run with no `bwrap` fails at its start naming the bubblewrap package, and one whose `bwrap` ran and refused the box (a user namespace AppArmor refuses, or one of its mounts) names bwrap's own line and both fixes.
A sandbox built inside the box (a test of the runner, a `test:skills` step's own `test:file`) adds no second one, since the outer box already holds its children and GitHub's runner refuses a user namespace inside one.
It skips the second box only on proof a variable alone never gives, a tmpfs at `TEST_SANDBOX_BOX` in its own `/proc/self/mountinfo` (`insideBox`), inside a scratch folder `makeScratch` marked, which only the outer box mounts, so a `TEST_SANDBOX_HOME` or `TEST_SANDBOX_BOX` set outside the box, one naming a system tmpfs such as `/dev/shm` included, still boxes, or still refuses.
The stand-in goes over each root tool's own file, since `bwrap` cannot bind over a symlink, which GitHub's runner image makes `/usr/bin/sudo`.
A test that reads the real home on Linux takes it from the passwd entry (`getent passwd`), since `os.userInfo().homedir` follows the sandbox's HOME (`tests/sandbox.test.ts`).
A test names each such tool bare, and `tests/live-tools-scan.test.ts`, over every `.ts` and `.py` test, fails on one named by an absolute path, on portless's CLI or bin path on any line, on a package runner (`bunx`, `npx`, `bun x`) given a proxy, service or `clean` verb, on a proxy start or stop or a service install in an argv, or inside a shell's `-c` string.
The scratch HOME's `.gitconfig` refuses git's network transports (`git`, `http`, `https`, `ssh`), so a remote a test names by its GitHub URL reaches no network and no credential helper: a test's remote is a local bare repo, a test that fakes ssh allows it in its own repo's config (`protocol.ssh.allow`), and a step that must fetch,
as `packages/scripts/src/skills-ref/cli.ts`'s uv fetch of its pin does, allows https on that call alone (`GIT_CONFIG_COUNT`).
A sandbox change that refuses a transport can pass on the Mac and fail only on CI: the Mac's warm uv cache already holds skills-ref's pin, while CI's cold one fetches it with git over https (`fatal: transport 'https' not allowed`).
Before you push such a change, run `test:skills` on an empty uv cache, which the sandbox keeps as given: `~/.playground/ops/run-slot.sh <your name> -- env UV_CACHE_DIR=<your scratch folder>/uv-cold bun run --cwd <worktree> test:skills`.
The sandbox hands its tests no `GIT_` variable, as `boxEnv`'s allowlist passes none, since a git hook exports `GIT_DIR` and `GIT_INDEX_FILE` and pre-commit runs tests, so a test's scratch `git init` or commit stays in its own folder; a test that needs a `GIT_` variable sets it on its own git call.
It hands its tests `NEXT_PUBLIC_PLAYGROUND_HOSTED` and `PLAYGROUND_HOSTED` empty, since `bun test` fills from the env files only a key its env leaves unset, so a worktree `.env` or a caller set for a hosted stack leaves every test on the local build's gates; a test of the hosted build sets the flag itself (`tests/api/hono/src/hosted.test.ts`).
Run from a folder with none of the env files `bun test` loads (`.env`, `.env.test` and `.env.test.local`, never `.env.local`), such as a skill-only worktree, `test-sandbox.ts` sets `SKIP_ENV_VALIDATION=true` for its tests unless the caller set it, so one whose import validates the env still runs there.
It does the same when those files leave a key the apps' schemas require unset or empty (`requiredKeys()` in `packages/env/src/gaps.ts`), as a fresh copy of `.env.example` leaves `POSTGRES_URL`, while a key set to a value its schema refuses stays validated.

## The run

`bun run test` builds `packages/*` first, because a test reaches a shared package through its `exports`, and an entry with no `bun` condition points at `dist` alone, so on a fresh checkout an unbuilt package resolves to nothing.
It builds them under `NODE_ENV=production SKIP_ENV_VALIDATION=true`, as `prebuildTests` does, since `@packages/auth`'s build validates the env, which a worktree with no `.env` leaves empty.
Only the shared packages (`@packages/*` and `@api/hono`) are built, never the web: a test imports the web's code by source path and never through a `dist`.
`bun run test:file <paths>` builds every shared package whose `dist` is missing (`@packages/*` and `@api/hono`, turbo's cache keeping the rest cheap),
beside the packages its files import whose `dist` is missing, is older than a file under its package's `src` while no stack runs in this worktree, or lacks a name they import, those reached through relative, `@/` and absolute imports into this checkout included,
and writes the data table's metrics when missing (`prebuildTests` in `packages/scripts/src/verify/prebuild.ts`, under `NODE_ENV=production SKIP_ENV_VALIDATION=true`), so a fresh clone runs it directly.
So a scratch test outside the checkout that imports its modules by absolute path builds what they import, while an absolute import into another clone stays unread.
It also builds a package whose dist file a test names by path (`packages/env/dist/gaps.mjs`), when that package's `dist` folder is missing.
A file that spawns a child process (`Bun.spawn`, `spawnSync`, `execFile`, the `$` shell), whatever the program, may start Bun on code the import scan cannot follow, a `bun -e` text, a path read at run time or a helper's binary in a variable, so test:file builds every shared package for it as it builds a package its files import, above (`tests/api/hono/src/bin/dashboard-thread.test.ts`).
`bun run check-types:tests` does the same for the packages its files import, type-only imports included, and builds `@api/hono`'s declarations, which the web's types import.
In the factory's main checkout each stops instead, naming your own worktree.
It runs the files in parallel (`packages/scripts/src/test-sandbox.ts`: `bun test --parallel`, the cores less one and at most 4, the slowest first by `tests/timings.json`, on GitHub the merged one below, which `bun run test:timings` rewrites after a run), then its `SERIAL` files one at a time.
`bun run test:file <paths>` stops before any test runs, naming each argument it cannot run, and runs a bun test file, a Python test, or a folder holding a test, while a path that is none of these, or a name filter selecting nothing, stops the run naming it, since bun reads a path it cannot find as a filter that matches nothing;
the Python tests run through the same `uv run` step test:skills uses, after bun's pass, so a broken bun does not wait them out.
In the factory's main checkout (`PLAYGROUND_REPO`) it also stops on any relative argument, naming `bun run --cwd <your worktree> test:file <paths>`, since a background task starts there and the main checkout follows `main`, so a relative path would test main's copy of the file and read green on code the branch never changed.
A test runs beside the others when it shares nothing with them: it binds port 0, starts its containers named `playground-test-<suite>-<pid>` (`testContainerName` in `tests/container.ts`; ops-sweep removes one whose pid no longer runs, so a run killed before its `afterAll` leaks nothing), and takes its scratch folders from `mkdtemp`; one that cannot joins `SERIAL`.
So does one that rebuilds a package or moves a file other tests read, since a worker beside it would read the half-built file, and one that hangs only beside other workers.
In the parallel pass each test gets 30s where bun gives 5s, since a test runs slower beside other workers; a test's own timeout wins, so read it first.
A parallel pass still running at its deadline (`TEST_PARALLEL_DEADLINE_MS`, 20 minutes, which the runner box's `suite.sh` raises and each of GitHub's shards lowers to 10, inside its own 20-minute `timeout-minutes`) is killed and fails, naming the files its workers still held, since bun's own timeout cannot stop synchronous code; the run's first line names the deadline it holds.
Each pass runs in a process group of its own, led by an `sh` that ends the whole group with `kill -KILL 0` once `bun test` exits, so a child a test leaves running, after the test passed or bun timed it out, ends with its pass (`runPass` in `test-sandbox.ts`): one stub hook once outlived its test with parent pid 1 until a reboot.
On Linux a child that leaves the group (a detached spawn) still ends with its pass, since the pass's pid view ends whole when its `bwrap` does; on macOS it is left to the nightly clean once its sandbox is gone and the session whose temp folder holds it has ended ([scripts/README.md](../scripts/README.md#a-factory-scripts-orphan)), so a test still ends each child it starts by its own handle.
GitHub runs the suite as shards rather than one run: `packages/scripts/src/test-shards.ts` packs the files longest first into as many shards as its budget of recorded file time (`BUDGET_MS`) needs, by `tests/timings.json`, where a file with none weighs the mean.
Each shard runs its own files through `test-sandbox.ts`, and the `Audit, Lint, and Build` check is green only when every shard, on both clocks (the clock-ahead pass, below), and the lint and build job passed.
A test that starts a container from a new image adds that image to the Suite job's `Pull the test images` step in `.github/workflows/auto-check-build.yml`, since a fresh runner's pull inside a 60s `beforeAll` times out; `tests/github/workflows/image-pull.test.ts` holds the step's list to the images the tests spawn.
A new test file needs no timing to run, and the split follows the suite with no hand run: each shard keeps its files' times as the run artifact `timings-<n>` (`TEST_TIMINGS_UPDATE`; bun times no `SERIAL` file, so those keep the committed time until a hand `bun run test:timings`).
The Shards job merges the newest passing run's over `tests/timings.json` before it splits (`packages/scripts/src/test-timings.ts`), every shard splitting by that one merged file.
Only a run from a branch of this repo counts, since a fork's run could upload any times; with none to read, the split keeps the committed file, and a shard whose artifact does not read is skipped by name.
No workflow commits the merged times, since a change reaches `canary` only through `pr:merge`, so the committed file stays a seed that `bun run test:timings`, committed in any PR, refreshes.
`tests/` is fork-excluded, so the root script no-ops where the directory is absent.
Pre-commit runs the tests that read every tracked file, since a commit anywhere can break them: `trace-count` runs the trace ratchet's test, `text-tests` runs the two tests that scan the tracked tree's text (`TREE_TEXT_TESTS` in `tests/lefthook.test.ts`, which holds both in that one job), and `no-raw-delete` runs `tests/no-raw-delete.test.ts`,
each on every commit but one of images and fonts alone.

## The clock-ahead pass

Beside the shards, GitHub runs the suite once more as `Suite (<n>, clock ahead)` jobs with every test's clock 30 days on, so a test that takes its clock from two sources (a fixed `NOW` passed to one call while another defaults to `Date.now()`) goes red on its own PR, not on the day the real clock reaches it.
Those jobs split on their own (`test-shards.ts legs`) without the exempt files, so they number fewer than the shards, and they keep no timings.
Run it locally with `CLOCK_AHEAD_DAYS=30 bun run test:file [paths]`: `test-sandbox.ts` then preloads `tests/clock-ahead.ts` into both passes and leaves out the files `CLOCK_EXEMPT` (`packages/scripts/src/clock-exempt.ts`) lists, named or matched, and names each named file it leaves out.
A test that reads the clock or a file's mtime runs `CLOCK_AHEAD_DAYS=30 bun run test:file <its path>` before review, since one PR's cache rows went red on the clock-ahead shard alone.
Give the shift to `test-sandbox.ts` alone, since `BUN_OPTIONS` breaks `bun run` itself.
The preload swaps in a `Date` that keeps running, moved ahead, because bun's `setSystemTime` stops the clock as it moves it (a 50 ms `Bun.sleep` read 0 ms elapsed, measured), which turns every test that times a wait red.
The shift reaches the test's own process alone, so two clocks stay real: a child process (spawn.sh, run-slot.sh, a CLI, a Python job), and a file's mtime, which the OS stamps.
A test that reads either against the moved clock is red on the shift alone, so it carries the moved clock to that source where it can: a bun child it starts through a helper of its own that passes the preload on (`inFixture` in `tests/dashboard-fixture.ts`), or a file it writes, whose mtime it sets from its own clock (`kept` in `tests/api/hono/src/lib/dashboard/inbox.test.ts`).
A time the test writes for a child to read (a kept failure's `failedAt`) is written by the child itself, before the code under test reads it, so both sides read the child's one clock (`readAfter` in `tests/scripts/hooks/no-outside-pr-code.test.ts`).
Where it cannot, its file joins `CLOCK_EXEMPT` with the reason.
Any other red in the pass is a real clock mix: fix it so the code takes one clock, passed in as `readHeld` takes its `now` (`packages/scripts/src/pr-merge/held.ts`).

## Traps

Write a run's output to a log file, then grep the log (`bun run test:file <paths> > <scratch>/run.log 2>&1`, then `grep -E "pass|fail" <scratch>/run.log`), since the run keeps its own exit status that way, and the `no-false-green` hook refuses a test run piped into `tail` or any other command ([scripts/hooks/README.md](../scripts/hooks/README.md#no-false-green)).
Commit before a red-first swap, so the file's edits sit in a commit, and restore it with `git checkout HEAD -- <file>`, which brings back that commit, where `git checkout -- <file>` brings back the index, which holds the swap once it is staged: on 1 Nov a worker's restore after a red-first swap took the file's uncommitted edits with it, and the work was redone.
A chain stops when that commit fails (`git commit ... || exit 1`), so the swap never runs over uncommitted edits: on 7 Nov trace-count refused a chain's commit, the chain went on to its swap, and the restore wiped the fix, re-applied from a patch.
The `no-extensions-write` hook refuses a write whose target or folder it cannot resolve, such as a `cp` loop to `~/.playground/scratch/<name>/keep-$(basename $f)`, or a `cd $D` followed by a write under `$D`: write each path out literally, or make the red-first swap with `git diff > <scratch>/patch` and `git apply`.
A red commit for a new module adds a stub of it, its exports typed and returning the wrong value or throwing, so the pre-commit check-types passes and the test fails on behaviour, not on a missing import.
`tests/install.test.ts` copies into its scratch clone the files the installer runs by walking every relative import from its entries (`withImports`), so a new import of an installer file arrives on its own.
A file the installer reaches by path rather than by import (a script `install.sh` or `link-skills.sh` runs, a JSON read with `readFileSync`) joins those entries, since a scratch clone that lacks it fails the test's install rows.
A test file is the smallest piece a shard takes, and its cases run one after another, so a file whose every case starts a subprocess (`spawn.sh` under `tests/scripts/spawn-fake.ts` or `run-slot.sh` under `tests/scripts/ops/run-slot-fake.ts`, spawn.sh's about 0.5s a case, measured) grows by that much with every case it gains.
Keep each such file under 60s on GitHub, since a file is the floor under its shard's time, by splitting it by `describe` into files of their own (`tests/scripts/spawn-*.test.ts`, `tests/scripts/ops/run-slot-*.test.ts`), with their shared helpers in their script's fake.
A test that starts `run-slot.sh` starts it through a tracked helper of `tests/scripts/ops/run-slot-fake.ts`: `runSlot` records the child and leaves it in the test run's own process group, so a TERM to the run still reaches it, and the fake's `spawn` starts through `runSlot` and adds the per-test sweep, whose `afterEach` stops the child when its test fails or times out first.
The file's `afterAll` then ends each `runSlot` child still unreaped, with the command group it owns, so a fail or a timeout leaves no child behind (five orphans once outlived their tests by days, each with ppid 1).
A test that checks a child has ended awaits the child's own `exited` promise, or checks its process group with `process.kill(-pgid, 0)` (`gone(pid, true)` in `tests/scripts/ops/run-slot-children.test.ts`), since on a loaded Mac the OS can hand a dead child's pid to a new process within a second, so `process.kill(pid, 0)` reads it alive again.
A fake ssh that git runs (`core.sshCommand` naming a script) starts twice for each read while `ssh.variant` is unset: first as git's `ssh -G` probe, which names no remote path, then for the read itself (measured).
Set `ssh.variant=ssh` in the test's repo (`git config ssh.variant ssh`, as `tests/packages/safe-delete/src/live-refs.test.ts` does), so each read starts the fake once and a test counts reads by the remote path each read logs.
`bun test` also loads the working directory's `.env` into `process.env`, so a test that hands `...process.env` to a child and writes a scratch `.env` for it drops each key that file sets, since the inherited value wins over the file.
A child started as `bun -e <code>` from the repo root resolves no workspace package, reading "Cannot find package '@packages/<name>'" with its `dist` present, since the repo root's `node_modules` links none of them,
so a child that imports one runs a file inside a package that consumes it, or takes that package as its working folder, and resolves through that consumer's own link (`api/hono/node_modules/@packages/`).
A test that imports a file of the web's client goes under `tests/web/next`, whose tsconfig extends `web/next`'s, since that file's own `@/` imports resolve only there: `tests/scripts/tsconfig.json` maps `@/` to `api/hono/src`.
Give every row of a `test.each` table as many values as its callback takes, padding the short ones (`rows()` in `tests/scripts/hooks/no-extension-repo-write.test.ts`), since bun:test hands a callback that takes more arguments than its row a `done` argument, which a synchronous callback waits on, so a passing test reads as a 30s timeout, and an async one takes it as its last value.
An `expect(...).rejects` or `.resolves` is awaited or returned, or is the body of an arrow helper whose every call is, since in bun:test one that is not passes while checking nothing; `tests/async-expect.test.ts` fails on any that is not.
A Bun SQL query is a lazy thenable that runs only when awaited, and `await expect(sqlQuery).rejects` never runs it, holding a sandbox worker to its deadline with no output: await the query in a helper and assert on the error's message (`refusal()` in `tests/api/hono/src/lib/store/store-db.test.ts`).
Bun's SQL double-encodes a JSON string bound as `${JSON.stringify(x)}::jsonb`, so the column stores a jsonb string rather than an object and `col ->> 'key'` reads null (measured on Bun 1.4.4: `jsonb_typeof` read `string`): bind the object itself, cast through text (`${JSON.stringify(x)}::text::jsonb`, as `packages/db/src/columns.ts` does), or use `jsonb_set` with a literal.
React Query's `refetchInterval` never fires under `bun test`, with real or fake timers: query-core (5.104.5) reads `isServer` as `typeof window === "undefined"` once at load, and its observer sets no refetch timer while `isServer()` is true.
Call `environmentManager.setIsServer(() => false)` (exported by `@tanstack/react-query`) in `beforeAll`, and `environmentManager.setIsServer(() => true)` in `afterAll`, so the file's own later tests run as on a server again:
measured in the parallel pass, a 50 ms interval fetched 8 times in 400 ms with it and once without, and a file run after it in the same worker, its restore removed, still read `isServer()` as true,
since each file loads its modules afresh.
Else test the query's options themselves (`inboxPolling()` in `tests/web/next/src/lib/tab-dot.test.ts`), or time the query in a child process that sets `window` before it loads query-core.
A test that builds a child's env from scratch rather than from `process.env` passes `UV_PYTHON_INSTALL_DIR` and `UV_CACHE_DIR` through (`drive()` in `tests/scripts/ops/unstick/run.test.ts`), since a child's `uv run --python 3.13` without them downloads a 66 MB CPython into the scratch home, and on a slow network each case's download outlasts its 30s and starts again in the next.
A case that waits on `fs.watch` waits on macOS's FSEvents, which at load5 13 dropped 6 of 15 changes to a file and delayed the rest by up to 4s.
Have the case fire the change itself through an injected watcher (`hubWith`'s `changed` in `tests/api/hono/src/lib/dashboard/hub.test.ts`), or shorten the rescan that catches a missed change (`INGEST_RESCAN_MS` in `tests/api/hono/src/bin/dashboard-ingest.test.ts`).
Keep one case on the real watcher, appending again until a change lands inside a named deadline, so a broken watch path still goes red ("a change fs.watch reports sends the transcript's new lines" and "a follower stores a line the watcher reports, before any rescan").
A speed test bounds work rather than milliseconds, since a bound in milliseconds fails when every core is busy: it caps the steps `stepsOf()` (`tests/scripts/hooks/pace.ts`) reads from `stepsTaken()` in `scripts/hooks/shell.ts`, which counts every `tick()`.
For a native step no tick counts (a regex, a string built whole), it bounds the step's CPU time over a same-length `echo` with `overBaseline()` (`tests/scripts/hooks/pace.ts`), since a busy machine stretches a long call's wall time far more than a short baseline's (x23 to x590 at load 44, measured).
Start a count of what waiting processes do on an event of theirs, never the clock, since a loaded Mac stretches wall time: the priority pick row in `tests/scripts/ops/run-slot-poll-cost.test.ts` counts from `run-slot.next` changing or the pick's look ending, and `starts()` in `tests/scripts/ops/run-slot-fake.ts` opens its window once each waiter has run a whole poll and none began a look.
Read each row's own time from its `(pass) ... [ms]` line, which bun prints in an agent session too, since the sandbox hands its tests no `CLAUDECODE`; a file's total hides which row is slow.
A timer or backstop case asserts the refusal under a test timeout tied to the constant it guards (the hung Docker case in `tests/scripts/hooks/no-mac-web-build.test.ts`).
Read a local run's timeouts against load5 (`uptime`'s middle figure) before you call them failures, since a loaded Mac stretches every case past a timeout that holds on an idle one: one local run of another repo's vitest suite at load 40 gave 28 failures, 19 of them its 5 s timeouts, while its CI was green at the same head (measured).
A case here times out at its own timeout, else at the parallel pass's 30s, or at bun's 5s in a `SERIAL` file (above).
While load5 is at or over the core count (`sysctl -n hw.ncpu`, on Linux `/proc/stat`'s `cpu<n>` lines), the figure `clone_brake()` in `scripts/ops/run-slot.sh` brakes clones at, CI is the signal: read the PR's `Audit, Lint, and Build` check, which holds every Suite shard, beside `test`, which runs `bun run test:skills`, and rerun a failing file alone locally once load5 is under the core count.
A file red beside the others and green on that lone rerun is a `BATCH-RED`: it gets one issue to root-cause it, or to delete the test with the reason, by [code-review-loop's step 2](../extensions/core/skills/code-review-loop/SKILL.md).
GitHub's ubuntu-26.04 runner runs uutils 0.10.0 as `mkdir`, which reports success when another process made the folder between its check and its own mkdir, so a shell lock taken with `mkdir` can have two holders there: 8 racing `mkdir`s gave more than one winner in 38 of 200 rounds, and GNU's, which the image keeps as `gnumkdir`, in none (measured).
A test that races such a lock puts `gnumkdir` first on its child's PATH as `mkdir` (`GNU_MKDIR` in `tests/scripts/ops/run-slot-fake.ts`), so it checks the lock as the Mac's atomic `mkdir` runs it.
A hook test file whose rows all hold one platform's reading pins that platform with `pinPlatform`, and a row that holds the other's wraps its one call in `as` (`tests/scripts/hooks/platform.ts`), since no-extensions-write reads a bare `cp` or `sed` as GNU's when `process.platform` is Linux, and CI runs on Linux.
A hook test that spawns a shell hands it a fixed PATH, `/usr/bin:/bin` with its own fake tools first (`as()` in `tests/scripts/hooks/no-outside-pr-code.test.ts`, `PATH` in `tests/scripts/hooks/no-mac-web-build.test.ts`), never `process.env.PATH`, since a tool installed on one machine's PATH changes what the hook finds and so its verdict.
The runner host's run clone is a fresh `git init` with no origin, and the host has no zsh, so a row reads neither from the machine it runs on.
A row that reads the checkout's GitHub origin hands the code under test a scratch checkout from `originCheckout` (`tests/machine.ts`), with a made-up origin, through the checkout argument `reposOf`, `factoryRepo`, `publicDraftHit` (`scripts/hooks/public-draft.ts`) and the guards' `check` take.
A row that starts zsh runs through `machineTest` with `zshMissing(<the PATH its child gets>)`: it skips with the reason in its name where zsh is missing, and fails under `CI`, whose Suite shards install zsh, so a lost install reads red.
test:skills' `hooks on main` step skips in a checkout with no origin and fails there under `CI`, whose checkout has its origin.
A test that lists items keeps to the items it made, filtering the list by their ids (the "an update starts unread" test in `tests/api/hono/src/lib/dashboard/inbox.test.ts`), since a file's tests share one database and another test's items can land in its list: with the clock 30 days ahead, one test's list took four older updates another test had left.
`Bun.which(name)` reads the PATH the process started with, so code under test that looks a tool up that way runs the real tool wherever one is installed and misses a stub the test prepends to `process.env.PATH`: look it up with `Bun.which(name, { PATH: process.env.PATH ?? "" })` (`packages/scripts/src/ops-ext-sync/sync.ts`), or take the lookup as a dependency the test passes in.
`Bun.spawn` and `spawnSync` find a bare program name the same way, so a stub `gh` the test prepends to `process.env.PATH` is never found (measured): run the code under test in a child bun whose `env.PATH` leads with the stub (`readAfter` in `tests/scripts/hooks/no-outside-pr-code.test.ts`).
A PATH shim for a bash script under test goes on its PATH before the script starts and acts once the test arms it (the `python3` and `stat` shims in `tests/scripts/ops/run-slot-look-marks.test.ts`), since bash keeps the path of each command it has run, so a shim written once the script has run that command is never called.
A test of a slow route runs past 12s on a real `Bun.serve`, since Bun.serve's default `idleTimeout` of 10s drops a quiet request at about 12s, not 10 (an 11s run stayed green with the route's `server.timeout(request, 0)` taken out, a 15s one went red with `ECONNRESET` at 12.1s, measured 12 Nov; `tests/api/hono/src/lib/dashboard/restore.test.ts`).
A test that needs a pid no live process holds uses one above every system's pid limit, such as 4194305 (Linux's `/proc/sys/kernel/pid_max` tops out at 4194304, macOS's pids stop at 99998), as `deadPid` in `tests/packages/scripts/src/pr-merge/merge.test.ts` does.
A small fixed pid fails it, since in a sandbox's pid namespace a test's own pid is small, so a fixed `<n>.json` can name the test itself, and so does a spawned-and-exited process's pid, which can be reused.
A test that needs a path outside the repo names a made-up file under its own temp folder (`join(dir, "outside.txt")`), never `/etc/passwd`, since GitGuardian, which checks every pull request, reads that path in a diff as a leaked password and fails its check.
A test whose result matches text in a path, such as a folder or session name, holds a made-up path outside `tmpdir()` (`/fixture/...`), since in a factory session on Linux the sandbox sits in that session's own temp folder, `/tmp/playground-<name>.<random>/test-sandbox-*`, so a path made there carries the session's name, and the test passes in one session and fails in another or on GitHub.
The sandbox stays in that folder, since the nightly clean reads the session a sandbox orphan belongs to from it (`SESSION` in `packages/scripts/src/ops-tick/orphans.ts`) and keeps a live session's orphans.
A fixture that stands for a large file is a small real file, never a sparse one made with `truncate -s`, since a sparse file takes almost nothing on disk but reads at its full apparent size: safe-delete measures apparent size, so a fixture taking 156K on disk read as 4.9G on the owner's removal card (measured, 17 Nov).
Edit a bash script only once every live run of it has ended, since bash reads a script a block at a time as it runs, so an edit made mid-run can change what that run does next.

## End-to-end tests

No end-to-end suite exists: `bun run test:e2e` matches no file.

The new-user gate is the one end-to-end run: `bun run gate:new-user <sha>` (`packages/scripts/src/new-user-gate/`) installs that sha the way `curl | bash` does, in a scratch HOME inside its box,
with stand-ins for claude, gh, brew, security and sudo, a logging curl (`stubs.ts`), a docker that reaches only the containers the box made (`docker.ts`) and its own portless proxy on port 14155.
That docker labels each container the box starts, lists only those, takes `run` with first run's own flags alone (no volume, host path or host network, a publish on 127.0.0.1 alone), and refuses and logs any other call or one naming another's container, which fails step 2.
It runs from a checkout at that sha, since the box is the calling checkout's gate code, and stops with exit 2 when that code differs from the sha's (the release skill's detached worktree).
The install runs on this host's OS, since `installEnv` sets no `INSTALL_OS` and install.sh reads `uname -s`.
The box's PATH (`boxPath`) carries this host's uv, linked alone into the box's `tools` folder, so install.sh's uv step downloads nothing on Linux, as `/opt/homebrew/bin` gives it on a Mac; a `curl` stand-in logs each URL to calls.log, so a download shows there.
The box is `makeBox`'s scratch folder `/tmp/pg-gate-<sha7>-<random>`, made in another parent folder with `--box <parent dir>`.
Before the install it checks that the box's zsh, plain and login, finds every stand-in in the box's stubs folder, and stops with exit 2 naming each one it finds elsewhere, so no job the box starts reaches a real binary.
Its claude runs a scripted session (`claude.ts`) for each launch spawn.sh makes: the dispatcher hands the typed task to the builder, the builder to a worker, and the worker runs `gh pr create`, calling no model.
The ops-usage job reads made-up usage windows from the box (`PLAYGROUND_USAGE_API`), so Usage shows a reading on a made-up login, once the installed sha's `scripts/ops/usage/run.py` reads that variable.
That login sits where the box's `security` reads it (`plantLogin` in `cli.ts`): the stand-in's Keychain file on a Mac, and on Linux Claude's `~/.claude/.credentials.json`, since install links Playground's own `security` (`packages/scripts/src/security/cli.ts`) first on PATH there.
When Alpha waits on a Claude account, the gate adds a made-up one through Add a Claude account and waits for its token where the box's `security` keeps it (`accountKept`): the stand-in's Keychain file on a Mac, and on Linux that `security`'s file under the box's `~/.playground/secrets/keychain/`.
It then checks the seven steps a new user meets (the install's finish, first run's database click, Alpha on the Dashboard, a routed task opening a PR, Usage, the Scripts group, the roll following main), prints PASS, FAIL or INCONCLUSIVE for each, and leaves a screenshot per step and the box's logs in the box's path plus `-shots` after removing the box, its processes and its container.
With `--pr <n>` it also posts its `## NewUserGate` verdict on that PR, which pr:merge's `new-user` gate reads, an INCONCLUSIVE refusing there like a FAIL.
Each child the box starts takes its env from `boxEnv`'s allowlist (`packages/scripts/src/box-env.ts`) with the box's HOME, since an absolute live-state path in this shell's env (`PORTLESS_STATE_DIR`, a herdr socket, the data folder) survives a new HOME: one clean once read the real `proxy.pid` and stopped the live proxy.
The clean stops the box's proxy with `-p 14155`, since a bare `portless proxy stop` probes 443, 80 and 1355 and stops whichever proxy answers, and a program missing from PATH, agent-browser among them, reads as exit 127 rather than a throw, so the clean always runs. <!-- kill-check: names only -->
A step's check and its screenshot settle are separate: a wait that only settles the screenshot runs inside the step's shot (`shotAfter` in `cli.ts`), since its timeout failed a step whose check passed (measured: a `networkidle` wait under load), and a settle or screenshot that fails is named on the step's report line while the step keeps its check's verdict.
A step whose check reads the page in a loop (Usage, the Scripts group) settles each read through `readAfter`, so a settle wait that times out counts as not settled yet and the loop still reads and judges the text.
Before the install it waits up to 10 minutes for this Mac's load to fall under the line spawn.sh's load gate holds a dispatcher's start to, and says how long it waited.
The box sets `PLAYGROUND_LOAD_MULT=10` (`BOX_LOAD_MULT`, printed at the start), so the host's other sessions never hold a start there, since the gate checks what a new user meets on a quiet Mac.
A step that fails while spawn.sh's capacity gate refused a start in the box (its `capacity.jsonl`, now its memory or usage gate) reads INCONCLUSIVE with that refusal, since the gate reads this Mac, not the build.
Run it through run-slot before each ship (the release skill's step 1); it exits 1 when a step fails or a `--pr` post fails.
Its last line, `New-user gate at <sha>: PASS` or `FAIL`, goes into the ship PR's body, where `ship:merge` reads it, the line and not the exit code, since a run whose only miss is INCONCLUSIVE exits 1 and reads PASS ([pr-merge's README](../packages/scripts/src/pr-merge/README.md#shipmerge)).
