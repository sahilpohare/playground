# The playground command

`playground` starts Playground from your terminal and opens the Dashboard. Your sessions run in herdr, and `playground view` shows them. Run it from any terminal. The Dashboard and its background jobs run in herdr too. `playground --help`, or `--help` after any command, lists every command. A word a command does not take, such as `playground ext list skills`, is refused before the command runs: it exits 2 and prints the command's usage, so a typo never reads as success. The `ask`, `changelog`, `dm`, `ingest`, `queues`, `thread` and `wa` commands, `playground picker`'s reason and `playground ext search`'s words pass on whole.

## Install

The [installer](/docs/install) sets the command up. In a checkout you cloned yourself, run `scripts/link-skills.sh` once instead. Either way `playground` is linked into `~/.bun/bin`, which a new terminal puts on your `PATH`, under that name alone. Check it with `command -v playground`.

## Start: `playground`

`playground` starts only what is down, then opens the Dashboard in your browser:

1. **herdr**: it starts each herdr server that is down, on the herdr version the repo pins, and brings back the sessions that ran there. It prints `ops-herdr: started playground` for each one it started, or `ops-herdr: all were up: playground, playground-probes` when none was down. When herdr cannot start, it says why and goes on with the rest.
2. **The Dashboard**: it sets the Dashboard's database to start again with Docker after a restart, and starts it when it has stopped, printing `The Dashboard's database was stopped; starting it`. When the Dashboard does not answer, it starts every background job that is not healthy, the Dashboard and the session follower among them, each in herdr's Ops workspace. They keep running when you close your terminal.
3. **The dispatcher**: when no session has the dispatcher's name (the setting `sessions.names`' dispatcher, `dispatcher` by default), it starts it as `playground dispatcher` does (below), and goes on when that start is refused.
4. It waits for the Dashboard to answer, then opens it. The first start can take a few minutes, so every 10 seconds it prints how long it has waited, as `Waiting for the Dashboard's API to answer… 1m 20s`, and once the Dashboard answers it prints `The Dashboard answered after 2m 10s`. When the Dashboard's background job exits while it waits, reports that the Dashboard could not start or that its address does not reach it, or the Dashboard's API answers with a redirect, it stops within half a minute and says why, and when the job stops checking in, it stops once the job has been silent for three of its minutes, rather than waiting the whole 15 minutes. Its last line reminds you that `playground view` shows your sessions.

When a step fails, the run ends with a **Left for you** list naming each step that failed and why, such as `The dispatcher didn't start: spawn.sh refuses dispatcher: …`, and exits 1.

When everything already runs, it only opens the Dashboard. Run it as often as you like.

On a fresh install, the first `playground` first cuts the Dashboard's own checkout (`.claude/worktrees/desk`) and installs it; the Dashboard then opens with **Let's check this Mac** in its chat. Before that first start, a command that runs in the Dashboard's checkout says `playground: no Dashboard checkout yet; run playground once to set it up` and stops.

## Start the dispatcher: `playground dispatcher`

`playground dispatcher` starts the dispatcher, the session you talk with, in a herdr workspace of its own, on Claude Code. `--harness codex` starts it on Codex instead (spawn.sh's `--harness`, which the Dashboard's **Start** passes from the `harness.alpha` setting), and `--brief <file>` starts it from that file in the data folder, the handoff Settings' **Switch Alpha** asks for; it takes nothing else.
It sets up first what the installer and `playground` would have, so the Dashboard's **Start** works on a fresh install: when a file the installer links into `~/.playground` is missing (the factory settings every session starts with among them) it runs the installer's linking step, `scripts/link-skills.sh`; when the pinned herdr is missing it installs it as `playground herdr pin` does; then it starts each herdr server that is down as `playground` does. When a step fails, it exits 1 with that step's reason and starts nothing.
Without `--brief`, its brief is `brief-<dispatcher>.md` in the data folder, copied from `scripts/briefs/dispatcher.md` when it is missing. While you leave the copy as it is, `playground update` keeps it the same as the template. Once you edit it, your edits stay, and the dispatcher gets the template's changes as a diff instead.
It exits 0 once the dispatcher starts, 3 when a session already holds the dispatcher's name (it starts nothing), and 1 with spawn.sh's reason when a gate refuses the start, or herdr's when herdr cannot come up.

## Start a manager: `playground planner`, `playground builder`, `playground ops`, `playground optimizer`

Each starts that manager as `playground dispatcher` starts the dispatcher, in a herdr workspace of its own, its brief copied from `scripts/briefs/<manager>.md` and kept up to date the same way.
The dispatcher runs the Planner, the Builder and Ops the first time it routes work to each, so no manager sits idle on your usage.
It runs the Optimizer at its own start: the Optimizer runs a retro after each ship to `main` and once a day, on the timed beats the factory sends it.
It exits 0 once the manager starts, 3 when it already runs (it starts nothing), and 1 with spawn.sh's reason when a gate refuses the start.

## View your sessions: `playground view`

`playground view` opens the factory's herdr server in your terminal, where your sessions run, so you never type a herdr path or setting. It takes nothing. When the server is down it says so: run `playground` to start it. Test sessions (probes) run on a server of their own, which this view leaves out.

## Check: `playground status`

One line for each part, for example:

```text
herdr factory: up, 12 sessions
herdr probes: down
Dashboard web: up
Dashboard API: up
Session follower: running
Dispatcher on Claude: running
GLM: not set up
```

Each herdr server shows whether it is up and how many sessions it holds, first, so it shows even when the Dashboard cannot be read. Each dispatcher shows by what it runs on (Claude or GLM). `GLM: not set up` means no GLM key is saved. `playground status` starts and stops nothing.

## Update: `playground update`

`playground update` brings your checkout up to the newest release, then moves the Dashboard to the newest commit of the branch it follows. It runs, in order, and stops at the first step that fails, naming it:

1. It fetches `origin/main` and fast-forwards your checkout onto it. A checkout left on another branch, such as `canary`, moves to `main` first when it holds no uncommitted changes, and the update says so; with uncommitted changes it stops there and changes nothing. A checkout with commits of its own on `main` cannot fast-forward, so it stops there too. When the release declares a dependency your checkout has not installed, it installs it from the release's `bun.lock` and `package.json` files before your checkout moves, so the hooks and jobs running from your checkout load the new code once what it imports is there. When the release deletes or moves a package, when your checkout holds changes of its own, or when that early install fails (it then puts those files back), it moves your checkout first and installs after, as it always did.
2. It runs `scripts/link-skills.sh`, so the home skill set takes a new or renamed skill, and prints `skills changed: <names>` with each one's folder in the checkout when the update changed a skill, since a running session's Skill tool serves the copy it started with, so a live session reads the new text from that folder.
   Then it brings each manager's brief in the data folder (`brief-<name>.md`, for the dispatcher, the Planner, the Builder, Ops and the Optimizer) up to its template. A copy you never edited, one that matches any committed version of `scripts/briefs/<manager>.md` (a newer one too, after `--to` moves back), is replaced with this release's template. A copy you edited stays as it is. Either way, when the template changed, the manager gets a message naming `brief-<name>.sent.diff` in the data folder, which holds the change. A manager that is not running gets that message the next time `playground <manager>` starts it. When this step fails, the update prints why and goes on.
3. It installs the dependencies when `bun.lock` or a `package.json` changed, and builds the shared packages when one of them changed.
4. It restarts each background job whose code changed.
5. With other machines named in `PLAYGROUND_PEERS` ([Dashboard](/docs/dashboard)), it moves each one's Playground copy, the one at the same place under its home folder as yours, to the same commit over ssh: it fetches, checks out that commit and installs. A copy with changes of its own, committed or not, on a branch other than `main`, or with another git worktree made from it, is left as it is. Each machine prints one line, `peer <name>: at <sha>` or why not, and none of them stops the update.
6. It moves the Dashboard to the newest build, printing each step; `Building…` lasts while the Dashboard is down for its production build, which can take a few minutes:

```text
Building…
Switching…
Updated to 3f9a2c1
```

When the machine is busy, the build waits its turn: it prints `Waiting for load: load5 is <n>, and the roll goes on under <n>…` or another `Waiting for …` line naming what it queues behind, then the next step once it starts. A roll still waiting after 30 minutes is not a failure: the update ends there, and the Dashboard moves on by itself once the build gets its turn. When the newest commit is the one running, it prints `Already up to date at <sha>`. When the new one fails its checks, the Dashboard goes back to the one it ran before: it prints `Going back…`, then `Failed: <reason>; back on <sha>`, or `going back to <sha> failed too` in place of `back on <sha>`. When the new one changed the database it stays on it, and the line says so. A commit that failed before is not tried again: it prints `Failed: <sha> failed its roll before`. Run `playground` first if the Dashboard is not running.

A Dashboard tab you have open reloads onto the new build by itself, once, within about 30 seconds of the switch, or when you come back to a tab that was in the background. It waits while a reply you typed on an Inbox card, or an answer to a session's question, is still unsent, or while a message you sent shows as failed, so those words are kept.

If an update stops partway, after your checkout has moved (a crash, a closed terminal, a step that failed), run `playground update` again: it still installs, builds and restarts what the release changed, since it compares against the commit the last finished update reached, which it keeps in the data folder's `ops/update-head`. With no record there, it compares against the last fast-forward onto `origin/main` in your checkout's git history and says so, or else where that first update started.

`playground update --to <tag>` moves your checkout to that release instead, back or on, with the same link, install, build, restart and peer steps, and leaves the Dashboard as it is, since it rolls on its own. A checkout with commits of its own stops before anything moves. `playground doctor` shows the release it is held at, and a plain `playground update` moves it on to the newest again.

## Check your install: `playground doctor`

`playground doctor` prints one line per thing Playground needs: `ok`, `MISSING` with the command that fixes it, or `optional`. It checks the tools on your `PATH` (`bun`, `claude`, `docker`, `gh`, `git`, `node` at 20.9 or newer and `python3`, with `uv` optional), your GitHub login (optional; without it syncing your extensions is off, and the line says so), the data folder it reads (`~/.playground`, or the one `PLAYGROUND_DATA_DIR` names), Playground's own herdr (`MISSING` with `playground herdr pin` as its fix when it is missing or changed, naming a herdr of your own on your `PATH`, which it leaves alone), that every link into your checkout points at a file that is there, the release your checkout is at and how far behind `origin/main` it is, and on a Mac that portless's proxy is running for the Dashboard's local address (`optional` while it is down, since the Dashboard runs on port 1355 meanwhile, with Settings' **Set up the web address** or running the installer again as its fix) and that each background job you turned on is loaded (on Linux, that each one's systemd user unit is active, and a `linger` line, `optional` while lingering is off, with `loginctl enable-linger <uid>` as its fix, [Ops jobs](/docs/jobs#on-linux)), on Linux arm64 a `test browser` line: `ok` when agent-browser, Playwright's pinned Chromium and agent-browser's settings are set up, else `MISSING` with each step ([Troubleshooting](/docs/troubleshooting#the-test-browser-on-linux)), on Linux a `browser certificate` line once portless has made its certificate: `MISSING` while a Firefox profile does not trust it, with the command and the button that add it, `optional` with a Chromium-family browser's own import, and `ok` for Helium once the `chromium-ca` root step's browser policy trusts it ([Troubleshooting](/docs/troubleshooting#the-browser-does-not-trust-the-dashboard-on-linux)), and, while the `ops-tunnel` job is on, a `tunnel` line: `ok` with the link to the Dashboard on another machine, or `MISSING` with why it cannot connect ([Ops jobs](/docs/jobs#reach-a-dashboard-on-another-machine)). It exits with an error when anything is `MISSING`, and changes nothing.

## Stop herdr: `playground herdr stop`

`playground herdr stop` stops every herdr server Playground started, each through its own socket in `~/.playground/herdr`, and no other herdr on your Mac. Every session running in them ends with it. It prints `ops-herdr: stopped <server>` for each one, or that none was running. The next `playground`, or **Start** in the Dashboard, starts them again; when the ops-herdr background job is turned on, it does so within a minute.

## Put herdr back: `playground herdr pin`

`playground herdr pin` downloads the herdr version Playground pins for your machine (a Mac with Apple silicon or Intel, or Linux on arm64 or x64) from herdr's GitHub release, checks it against the SHA-256 written in Playground, and only then keeps it at `~/.playground/bin/herdr`. A download that does not match is refused, naming both sums, and nothing is installed. When the copy already matches, it changes nothing. `--check` only reads the copy and exits 1 when it is missing or changed; `--asset <file>` installs from a file you downloaded instead. A herdr on your `PATH` is yours: Playground never runs it.

## Show the version: `playground version`

`playground version` prints your checkout's tag and commit, your login scope's last commit in the extensions, which new sessions read (`none rendered` until there is one), and your Claude Code version.

## Move a machine onto Playground: `playground migrate`

`playground migrate --archive <checkout> --pre-squash <sha> --org <org>` runs once, on a machine that ran the factory before Playground. First it moves the old data folder in `~/.claude` to `~/.playground` and leaves each old name as a link to it, so a path written before the switch still reads. It reads each value the old tree held from the archive checkout, at its `canary` (or `--old <rev>`) and at the pre-squash commit, and writes it into your login's scope: the settings and the release owners' list. Your own rules come with your private extension, so it reads none. The managers' session names come from this machine's roster, `ext.order` puts your login first and the org `--org` gives after it, `ext.links` links your login to every repo and the org's extension to the org's repos and every repo (or, when your login's scope holds the older `orgs.map` and `orgs.always`, links each owner `orgs.map` names to its org and each `orgs.always` org to every repo), `factory.archiveRepo` is the archive checkout's GitHub origin, `factory.repo` is this checkout's, and `factory.publicRepo` is this checkout's too. It also brings the hand-made skills into the org's scope, unless that scope's clone already holds them. A value already set stays as it is, so a second run changes nothing. Then it moves the machine itself, so run it with the Dashboard's job stopped. Every old name it moves comes from the migration table the archive checkout holds at the pre-squash commit (its `.github/notes/migrate/table.json`): each renamed job takes its new name in `jobs.json` and in your settings, the dropped jobs leave `jobs.json`, every job's path into an old data folder points into `~/.playground`, the old script copies move into the data folder's `archive/` folder, a copy whose name `archive/` already holds staying where it is and the command exiting 1, the state folder and files the table lists move to their new names, and each variable your shell profiles and LaunchAgents set under an old name takes its new one, with the old file kept beside it as `<file>.pre-migrate`. Last, whatever the other steps did, it runs `playground herdr pin`, which puts Playground's own herdr in place. `--dry-run` prints what each step would write and downloads nothing. A step that finds no value names the file it read, the other steps still run, and the command exits 1.

## Remove: `playground uninstall`

`playground uninstall` stops and removes each background job that runs from your checkout or the data folder (on Linux, each systemd user unit it disables), stops the Dashboard, removes the home skill set (`ws-home@ws`) and its `ws` marketplace from Claude Code when it lists them, and removes every link into your checkout: the skills, the command and the links in the data folder. It keeps the data folder (`~/.playground`) and the Dashboard's database, and says so. When the Dashboard does not stop, it says so with the reason, removes the rest, and exits with an error. `playground uninstall --purge` also removes the database and moves the data folder aside to `~/.playground-purged-<UTC time>`, which it prints, after you type `purge` to confirm; any other answer removes nothing. Delete that folder yourself once you no longer need it. The checkout itself stays: delete its folder yourself when you no longer want it.

## Add a session: `playground add`

`playground add` starts a session through `scripts/spawn.sh`, so every check `spawn.sh` makes applies: the number of sessions, the machine's load and memory, room for a new worker's heavy runs, your usage, and a name already in use. When a check refuses, `playground add` prints the reason and exits with an error. One start runs at a time: a second one while another runs is refused, so try it again once the first ends.

- `playground add` starts a worker under a fresh name, and `--kind runner` starts a runner instead. `playground add worker-otter` uses your name, which starts with its kind (`worker-` or `runner-`). A worker needs `--title "<title>"`, a plain title of up to 40 characters saying what it does, which the sidebar shows. A runner takes its name as its title and no `--title`. Add `--brief <file>` for its first brief (a file under `~/.playground`, by its name there or its full path), `--model <id>` for its Claude model, `--account <email>` for the Claude login it runs on, or `--backend glm` to run it on GLM. While your settings list a Claude account (`usage.accounts`), a worker needs `--account`, and the refusal lists them in order. With no brief, the new session tells its lead that it is up and waits for a task.
- `playground add --dispatcher --backend glm` starts a second dispatcher on GLM, so it keeps working when your Claude usage runs out. It prints `Started a second dispatcher on GLM`. It runs on GLM alone, since a second dispatcher on Claude needs a second Claude account.

Starting a manager (`--manager`) is not ready yet; it says so and starts nothing.

## Keep a page: `playground page`

`playground page <file.html> --title "<title>" --by <session> [--for <session>]` keeps an HTML page an agent made for you.
It copies the file into the previews folder (`~/.playground/previews`) under its own name, with `-2`, `-3` added when the name is taken, saves the title beside it, records who made it (`--by`) and for whom (`--for`) in `pages.jsonl` there, and prints the copy's path.
It opens nothing on your screen: the agent sends you the page as an Inbox card, and you read it in the Inbox's viewer.
The page then shows on the [Pages](/docs/agents#pages) tab of both sessions and of your chat, and in the Previews app.
It refuses a file that is not an HTML page, and a `--by` or `--for` that names no session on the roster.

`playground page --remove <file.html>` takes one kept page off the Pages tab, named by its file name or by the path `playground page` printed.
It adds a line to `pages.jsonl` that drops the page's record, the same line the Pages tab's delete writes, and moves the page's HTML, its caption and the PDF beside it to the trash, printing each one's id for `playground rm --restore <id>`.
It refuses before it moves anything: a page `pages.jsonl` does not list, a path outside the previews folder or with a `..` step, a previews folder that is a symlink, a page file or `pages.jsonl` that is a symlink or a hard link, a file over 20 MiB, and a page whose files would take more of the trash's three moves a minute than your session has left.
The HTML moves first and the record drops second, so a refused move leaves the page listed; when `pages.jsonl` cannot take the line, the HTML comes back from the trash and the page stays.

## Wait on CI: `playground ci-wait`

`playground ci-wait <pr>` waits until each check `pr:merge` needs, `Audit, Lint, and Build` and `test`, exists at the PR's head and has finished, then prints each result and exits 0 when all passed, else 1.
It reads GitHub every 5 minutes, waits out a rate limit, and starts over when a push moves the head.
When a check's workflow run ends without creating the check, it exits 1 and names the `gh run rerun` that brings it.
When the PR conflicts with its base, it exits 1 at once with `#<n> conflicts with <base>: no CI runs until <base> is merged in`, since GitHub starts no CI on such a PR; while GitHub has not yet worked out whether an open PR merges, it waits, and a merged or closed PR, whose answer stays unknown, has its checks read as they stand.
When GitHub does not know the PR or repo, or refuses your login, it exits 2 at once.
`--repo <owner/name>` points it at another repo; it reads the factory's own by default.
Run it as a background task, and read the head's checks once more yourself before you call it green.

## Wait for alerts: `playground alerts-wait`

`playground alerts-wait <name>` waits until the next line in the outbox addressed to `<name>`, prints it, and exits: a stuck session's alert or the relay watch's late-stop line first, else any job's line, such as a firefighting heads-up to the Builder.
Each name keeps its own place in each queue, so a printed line is not printed again, and a line addressed to another session waits for that session.
A manager keeps it running as a background task and starts it again after each line, so it hears in a second or two rather than waiting for the relay.
A session on another machine keeps one running too, for the lines `playground send` brings it, which print led by `[ops-peer]` and the sender's name.

## Message a session on another machine: `playground send`

`playground send <name> <text>` queues one line, `{at, from, id, text, to}`, in the outbox's `ops-peer.jsonl`, where `from` is your session's name, and prints `queued <id> for <name>`.
The [`ops-peer-relay` job](/docs/jobs#carry-messages-to-another-machine) copies it to the other machine, where that session's `playground alerts-wait` prints it.
The text goes on one line, and a line over 16 KB is refused: send the path of a file that holds the text.

## Start a local model: `playground model use`

`playground model use <name> [--machine <name>]` starts the vLLM server in `~/models/<name>/` on one machine: the one `--machine` names, else the one whose `localModels.hereModel` (this machine) or `localModels.peerModel` (the peer) names that model, else the peer.
It sizes the server from that machine's free memory as it starts: the share is what is free above the machine's reserve (`localModels.hereReserveGiB` here; on the peer the 15 GiB floor plus `localModels.boxLanes` runs of `localModels.boxRunGiB`), capped at the model's working share in `localModels.models`, and `--max-num-seqs` is the KV cache that share leaves at 64k tokens a session.
It hands `serve.sh` the size as `CONTAINER`, `PORT`, `GPU_MEMORY_UTILIZATION` and `MAX_NUM_SEQS`, and refuses a `serve.sh` that does not take all four from its environment.
When the reading holds a session of the new model beside what runs, it starts beside it, under its own container (`local-vllm-<name>`) on the next port, 8000 then 8001.
Otherwise it swaps: it holds new starts there, waits up to 30 minutes for the running model's requests to finish, stops that model by the container name it started it under, and sizes again.
It refuses with the memory reading when not even one session fits, stops a server whose load takes the machine under 15 GiB free, and leaves alone any container it did not start.
Each server it starts is kept in `<data>/models/state.json`, under `machines.<machine>.servers.<model>`: its container, port, share, most sessions and start time.
The ops-tick beat `model-keep` keeps each machine's kept model up: it starts it when it is down, and brings it back once another model there sits idle `localModels.idleMinutes`.
A `/metrics` that answers nothing counts as no idle time while `docker inspect` reads the container as running, as a swap's drain reads it, so a server too busy to answer is never stopped mid-request.
On each beat it also reads every server's `/metrics` and keeps the snapshot beside the server in the state file, with the speed since the beat before: `decodeTps`, generated tokens over decode seconds, `ttftMean`, the mean wait for a first token, and `waiting`, the requests queued.
A window with no generation or no first token, a `/metrics` that answers nothing, and a speed older than 15 minutes hold no samples.
`spawn.sh --backend local` reads that speed against two floors, `localModels.minTps` and `localModels.maxFirstTokenSeconds` ([The keys](/docs/extensions#the-keys)): it refuses a start while a request waits, while each live local session's speed times n/(n+1) falls under the speed floor, with n the live local sessions, or while the first-token wait reaches its floor.
The peer's servers reach this machine through the [`ops-model-tunnel` job](/docs/jobs#reach-the-model-servers-on-another-machine).

To copy a model's folder to the other machine, use `rsync -a --copy-unsafe-links` (or `-L`), since a Hugging Face repo's files are links into its shared `hf/hub/blobs/` folder, which a plain `rsync -a` copies as links that point nowhere.
Then check the copy: `find <dir> -xtype l` prints nothing once every link resolves.

## Answer a permission prompt: `playground picker`

`playground picker <session> allow <key>` or `playground picker <session> deny <key> "<reason>"` is how a manager answers the permission prompt a session it runs is stuck on, once that session's alert reaches it with the command and its key.
`allow` presses Yes, once, in the session's own pane after reading that the pane's prompt shows that command; `deny` presses No and sends the session the reason, so it can try a simpler way.
A hook that asks to confirm a call draws a permission prompt too, and a prompt whose long command runs past the top of the pane still counts: `picker` checks that the lines still showing end the command.
Each answer is a line in `ops/picker.log` under `~/.playground`, naming who answered, the session and the start of the command.
When one of your standing rules settles the answer, `--rule <name>` after the key, a hyphen for each space in the name (`--rule local-page`), records that rule in the line and in a deny's message; a name that matches no rule presses nothing.
It refuses anyone but the session's manager or the primary dispatcher, a deny with no reason, a session that is not running or runs in no herdr pane, a dispatcher's own prompt, a key that no prompt showing matches, and a prompt that may be another waiting call's, as a subagent's file or URL prompt always is while its parent waits.
For that last one, since a herdr pane takes no key from a session's hand, the manager closes the session with `spawn.sh close` and resumes it under its name by its session id, with the reason as its brief and, for a reviewer or tester, `--pr` with the PRs its roster row names, so the prompted call never runs.

## Delete safely: `playground rm`

`playground rm <path> [--reason "<why>"]` moves a file or folder into the trash, `~/.playground/trash`, rather than deleting it, so it can come back for 7 days.
Each delete lands in `trash/<UTC-ts>-<session>/<n>/`, and a line in that folder's `manifest.jsonl` records where it came from, who deleted it, why, and its size and file count.
Its `node_modules` folders and `web/next/.next` are removed from the trashed copy, since a `bun install` or a build rebuilds them, and the move's and the restore's lines both say so.
The dashboard moves its own leftovers there too: a fixture stack's scratch folder and a Vibeground's record and `.env`, and so do the factory's scripts: `sync:shadcn`'s old `ui/` folder, the skill folders `vendor:upstream` replaces, and a leads worktree whose first install failed.
`playground rm --list` prints what the trash holds, and `playground rm --restore <id>` puts one item back where it was, refusing when something already stands there, and a worktree's restore also refuses as its `--worktree` lines below say.
It refuses, before moving anything:

- The main checkout and everything in it but the worktrees under `.claude/worktrees/`.
- A path over 5,000 files or 2 GB (an ended session's whole `scratchpad/<folder>/` or `scratch/<folder>/`, a retired data folder, a folder inside the caller's own `scratchpad/<name>/` and the caller's own temp folder `/tmp/playground-<name>.*` skip the file count and keep the 2 GB cap), and a fourth delete within a minute from one session; these and a protected path are also sent to the dispatcher, a session at the per-minute limit once for each burst, however many deletes it then tries.

`playground rm --worktree <path>` removes a worktree under `.claude/worktrees/`, the main checkout's or another repo's: it refuses the main checkout's worktree on the `live.branch` branch (the live Dashboard's checkout) outright, `--discard` included, since it moves only by `.agents/dashboard/live.md`'s roll, and every worktree while that setting cannot be read; it refuses when the roster cannot be read, when a live session on the roster holds it by its branch, its name (but a manager's, below) or a pull request its row lists as its `pr` or in its `prs`, by that number in the worktree's folder or branch name or as the worktree's own pull request (the one GitHub finds for its branch), unless the row's pull requests are its one hold and GitHub reads that one as merged with the worktree at or behind its head, when a running `node_modules` clone reads from it or copies into it, when a symlink outside it points into it, when a process works inside it, when `git status --porcelain` lists an uncommitted change in it (the refusal names the count and the first three paths), or when its HEAD's work has not landed on `origin/canary` (for another repo's worktree, on that repo's default branch) or on a remote branch that still holds it (below), then moves it to the trash and runs `git worktree prune` in its own repo.
A folder in another repo's `.claude/worktrees/` counts only when git proves it that repo's worktree: its `.git` file points into the repo's `.git/worktrees/` and the repo's `git worktree list` names it, so a plain folder, a clone, the repo's own checkout and a worktree elsewhere stay refused, and plain `playground rm` refuses a proven one, naming `--worktree`.
Its pull request is read through `gh` in the worktree itself, so from that repo's own `origin`, and every rule below holds for it as for one of the main checkout's.
A folder outside `.claude/worktrees/`, but a model test's replay worktree (below), is refused with `--worktree` or `--discard`, and the refusal names the route that works: plain `playground rm <path>` up to 5,000 files or 2 GB, and the lead's cleanup for a bigger tree.
A session holds it by its name when the folder's or the branch's name, after its `PG-<n>-` prefix, is that name or starts with it and a `-`, so `lint` holds `PG-12-lint` and `PG-13-lint-job` while `PG-5-splint` stays free of it.
A manager seat, a session whose roster kind, or else its name, places it as a manager (`ops`, `dispatcher`), holds none by its name alone, since its name names the work it routes, while its branch and its pull request still hold.
A session's id that holds a digit (`k3m9px` of `k3m9px-worker`) holds any folder or branch whose name contains it.
A live session that holds it in none of these ways is not seen as holding it; the trash keeps the worktree 7 days for `--restore`.
Its trash entry keeps the branch, the commit and the record folder of the worktree in its own repo, which the prune deletes, so `--restore` brings it back as git reads it: it writes a gone record folder back, recreates a gone branch at that commit and rebuilds the index from it, keeping the files, and leaves a record folder still there as it is; it refuses before the move when the branch now points at another commit, naming both, or when the commit has gone, naming it and, for a worktree on a branch, the `git branch` command that recreates the branch once the commit is fetched.
When its `git branch` or `git reset` fails after the move, it exits 1 with `restored <path>, but git cannot read it yet`, naming the failed step and git's error.
`--pr <url>` names the pull request whose session used the worktree, so another live session of that pull request, its merging worker or a sibling checker, no longer holds it by that number alone, whether its row lists that pull request as its `pr` or in its `prs`, while another pull request the row lists still holds; with `--discard`, only once that pull request reads merged or closed, so a live checker keeps its clone of an open one. A hold by branch, name, clone, link or process still counts.
Once the worktree's own pull request (`--pr`'s, else its branch's) reads merged or closed and the worktree sits at that pull request's head, a live session that holds it by its branch or by that pull request's number holds it no more, and the run prints `<path> is freed by #<n>, which reads <state>, past <name>'s roster row (<status>)`; commits past that head keep every hold and the run names them, as does a hold by name or id, by another pull request's number while that pull request reads open or closed or the worktree has commits past its head, or by a clone, link or process, and a state GitHub cannot read keeps every hold.
A worktree that sits clean (`git status --porcelain` prints nothing, untracked files included), detached, at a commit its base holds (`origin/canary`, or for another repo's worktree that repo's default branch, below) is held by no live roster row, since it reads that base and holds no session's work, and the run prints `<path> sits clean, detached, at a commit <base> holds, so <name>'s roster row (<status>) holds it no more`; a clone, link or process inside it still holds it.
A process inside it is named in the refusal, `<path> is held by pid <n> (<command>) working in <folder>`, and nothing is signalled, so the session that started it closes it by its own handle.
When that process is agent-browser, the refusal adds its session, from its `--session` argument or its socket's name, and the close that frees the folder: `agent-browser session <name>, which agent-browser --session <name> close frees`.
For a daemon that shows neither, the refusal names no session, since a guessed name could close another agent's browser, and has you close your own by its name: `an agent-browser session whose name it does not show, so close your own by its name: agent-browser --session <your-name> close`.
A clone is read from run-slot's clone holder record (`run-slot-clone.holder` in the data folder's `ops`), which names its source and destination while its pid lives, since the clone's `cp` only reads its source and works in whatever folder run-slot was called from, so neither end need be a process's working folder; the refusal reads `<path> is held by <session>'s node_modules clone (pid <n>) from <source> into <destination>`.
The record is read again right before the move, after the walk that counts the worktree's files for the trash, since a large worktree's walk takes seconds and a clone can start inside it.
A link is looked for in each other worktree under the main checkout's `.claude/worktrees/` and the worktree's own repo's, each `makeScratch` scratch folder in a temp folder, and each session's scratchpad with the folders directly in it, at their top level and one level into their `node_modules`; the refusal reads `<path> is linked into by <link> -> <target>: repoint or remove each link first`, naming the first three links and counting the rest, and a link whose target is missing or lies outside the worktree does not count.
Its work has landed when each file HEAD changed since its merge-base with `origin/canary` reads the same there, or, since canary squash-merges and may change those files again, when GitHub lists a merged pull request holding HEAD's commit; a review clone detached at a merged pull request's head lands the same way.
Another repo's worktree is measured against that repo's default branch in place of `origin/canary`: the branch `origin/HEAD` names, else the one `gh repo view --json defaultBranchRef` names, and the refusal names the branch it measured against, or says that neither names one.
Either repo's worktree also goes when a remote branch holds HEAD, and so every commit HEAD holds, as the remote itself reads now, so a stood-down PR's tree whose branch origin holds needs no `--discard`.
A remote-tracking ref is only the remote's last fetch, so every path that asks which commits a remote holds (this one, `archiveUnlanded`, `--discard`'s bundle and the nightly clean's other repos) reads each remote live through `unpushed` (`packages/safe-delete/src/index.ts`), whose `liveHeads` (`packages/safe-delete/src/live-refs.ts`, which the push scans share) runs `git ls-remote --heads` per remote, with `BatchMode` and a connect limit added to the ssh command git would run (`GIT_SSH_COMMAND`, else `core.sshCommand`, else `ssh`) and a 30-second limit, so a remote that prompts or hangs reads as unreadable, and a remote branch counts only at a sha this repo has; a remote it cannot read holds no commit.
Here a branch counts only when its live sha is HEAD or has HEAD as an ancestor.
The run then prints `<path>'s commits are all on <remote>/<branch>, which the remote still holds, so no work is lost`, and a branch the remote has deleted or moved since, a remote that cannot be read, or a commit past the pushed branch keeps the refusal.
Another repo's worktree for which `gh` answers that its branch has no pull request, and whose only unlanded work is commits, takes no `--discard`: `archiveUnlanded` (`packages/safe-delete/src/index.ts`) first archives the commits no remote holds now, as `unpushed` reads them (above), by `git format-patch`, into the data folder's `scratchpad/archive/<repo>/<worktree>-<HEAD sha7>/`, reading a folder already there as it is, and lets the move go only when the archive holds a patch for each of those commits, by each patch's `From` line; a patch for another commit, left by an earlier run before a remote took that commit, does not count against it.
A read `gh` cannot make, two pull requests answering, or one that is not the worktree's own keeps the refusal as it reads for any worktree, and a failed write, a short archive or a merge commit, which `git format-patch` skips, keeps it too, naming why; so does a remote `unpushed` cannot read, which leaves no tip to archive past, so the run writes no patch and names that remote (`its remote origin could not be read, so its work stays until it answers`), while `--discard` still takes the tree through its one bundle; the main checkout's worktrees never take this route, and the archive stays in the data folder on this Mac, where `git am` replays it.
`--discard` lets the uncommitted changes and the unlanded work go, and both refusals name it; it never passes a holder, a clone, a link or a process.
`--discard` asks no decision, of a session or a terminal alike: right before the move it writes the commits no remote holds now, as `unpushed` reads them (above), into a git bundle beside the move in the trash, `<worktree>.bundle` with `<worktree>.shas` (each sha and ref) in the move's `<UTC-ts>-<session>` folder, and a bundle it cannot write keeps the worktree.
The bundle is never pushed, since the repo is public and unpushed work has been through none of the leak checks; the move line names it with `git -C <repo> fetch <bundle> HEAD`, which brings those commits back, and the trash purge takes it with its folder.
The pull request a hold is freed by is the one `--pr` names, else the one whose branch the worktree has checked out, read through `gh`, and it counts only when exactly one pull request answers, it is the worktree's own (its branch is the worktree's, or its head is the worktree's HEAD, so a stacked branch does not pass under its parent's), and its head is the worktree's HEAD or an ancestor of it; an open one, none, or a state `gh` cannot read frees no hold.
Discarded files go into the trash with the worktree, so they come back with it, and a restore whose commit is gone names the bundle's `git fetch`.
A worktree whose trash entry holds no git record, one trashed before the entry kept it or one git could not read, comes back with its files alone, and git does not list it as a worktree.
`playground rm --worktree <path>` also takes a model test's replay worktree: a folder in a row of `~/models/kit/runs/`, or one inside a folder the machine record holds, that git proves a worktree of the main checkout, detached at a commit `origin/canary` holds.
Under `~/models/kit/runs/` every change in it is the test's output; elsewhere it refuses one with a tracked edit.
A process working in it holds it, as one holds any worktree, and it takes neither `--discard` nor `--pr`.
It first writes the worktree's work, `git diff HEAD` with its untracked files, to `<name>.diff` beside it, so no graded attempt is lost, then removes it through the main checkout's own forced `git worktree remove`, never the trash.

`playground rm <path> --card <id>` removes a path the owner approved on the nightly clean's unused-space Inbox card: only one that card's Remove names on this machine, at the size the card showed, and only while the card reads as the nightly clean last wrote it and the answer came after that write, written as one absolute path with no `..` and reached through no symlink.
Model weights, a `.gguf` or `.safetensors` file under `~/models/` or a recorded folder or a repo folder directly in `~/models/hf/hub/`, are deleted outright, since they download again and can outgrow the trash's disk, with a line in the trash's `deleted.jsonl`; anything else moves to the trash whole, past the file and size caps, a `rehearse<N>` folder in a session's scratchpad included, and `--restore` puts it back.
When the machine record holds that exact path, its entry is dropped.

Ops empties the trash every hour: each delete over 7 days old goes, and the oldest go sooner while the disk has under 50 GB free, at any load. Each hour it also strips every delete's `node_modules` folders and `web/next/.next`, which a `bun install` or a build rebuilds.

## Keep a record of what the factory adds: `playground record`

Each machine keeps a record of every path the factory put on it: `machine-record.json` in your data folder, one entry a path with why it is there and how to undo it.
`playground record add <path> --kind <kind> --why "<why>" --undo "<undo>"` adds one, and a path the record holds already changes nothing; `playground record drop <path>` takes one off.
An Inbox root step that ran, `link-skills.sh`'s links, and the run folder and Postgres image the runner box's heavy runs use add their own paths, so you add by hand only what you made by hand.
`playground record seed` fills the record once on a machine from your data folder's `bundles/footprint.md` and that machine's undo note, `bundles/<machine>-undo.md`, and keeps what the watched places hold then as its baseline, so the first check names only what came after.
`playground record check` compares the record with the watched places: the home folder's top level, `~/.bun/bin`, `~/.cache`, `~/.config`, systemd user units, `~/.local/bin`, Docker's images and containers, and the root steps' folders.
It prints one line a finding: `misplaced` for a new path outside the folders `paths.factoryHomes` names, `unrecorded` for one inside them, `gone` for a recorded path that is not there, and `unreadable` for a place or path it cannot read.
Ops runs it every night at 3:45 on this machine and on each machine `PLAYGROUND_PEERS` names, and sends each finding to Ops.

`playground rules` prints the standing rules a factory session starts with, each by its first line, with your settings' values in place of each `{key}`.
`playground rules <name>` prints one rule whole, its what and why, the same way; a name of two words takes a hyphen (`playground rules local-page`).

## Change a setting: `playground settings`

`playground settings list`, `get <key>`, `why <key>`, `set <key> <value> --reason "<why>"` and `reset <key> --reason "<why>"` read and change your settings in your extensions folder, with no Dashboard needed.

`playground settings import-jobs <jobs.json>` brings a hand-kept `jobs.json` into settings once, at the switch, and a session's import is refused but for `--dry-run`, which lists what it would write; [Ops jobs](/docs/jobs) has the rest.

## Use your extensions: `playground ext`

`playground ext list` names your extensions in order, core last, with each one's repo, linked orgs and item counts; with `--scope` or `--kind` it lists items. `show`, `put`, `why`, `diff` and `search` read your extensions and put an item's next revision, from a file, a skill's folder or standard input, with its reason and any `--attach` files, as one commit in its scope.
`playground ext init [--yes | --dry-run]` reuses your private repo, or makes one once you answer `y` (`--yes` off a terminal), and clones your login's folder from it (`--dry-run` prints the login, the repo and whether it exists, making nothing), and `playground ext sync [<scope>]` syncs each scope with its repo now ([Your private repos](/docs/backup#your-private-repos)).
`playground ext add <name> [<owner/name>] [--yes]` does the same for another extension, asking the same way before it makes a repo: it clones `<login>/playground-<name>` (or the repo you name, which it records in `ext.repos`) into its folder, keeps any files already there, and puts it last in `ext.order`, linked to no org until you link it; core is read-only, so `ext add core` exits 2.
`playground ext add <name> [<owner/name>] --dry-run` makes nothing and prints, as JSON, the repo it would use, whether it is on GitHub yet (a public one is refused) and how many entries its `skills/` holds.
`playground ext order <name>...` puts the names given first, `ext link <name> <org|*>` and `ext unlink <name> <org|*>` choose whose repos read an extension (`*` is every repo), and `ext remove <name>` takes one out of all three keys while its folder stays.
`playground ext export <folder>` clones every scope into a new folder, and `playground ext import <folder> [--dry-run]` brings one back, showing what it would change first with `--dry-run`.
`playground ext import --from-tree <folder>` puts each guard's list file in the folder into your login's lists ([How sessions read it](/docs/extensions#how-sessions-read-it)).
`playground ext lock` locks the extensions folder and everything in it on macOS, so a plain write from any program is refused while every `playground ext` and `playground settings` write lifts the lock for itself and locks it again: on the one extension's folder it changes, or on the whole folder when it changes the folder's own files or adds an extension, and `playground ext unlock` clears it until the ops tick locks it again, within 5 minutes.
`playground ext score`, `accept` and `reject` judge a proposal with a reason, `score` from a session other than the proposal's author, by its registry name, and `accept` with no `PLAYGROUND_ROLE` set ([Review](/docs/extensions#review)).
[Settings and extensions](/docs/extensions#extensions) and [Export, import and backup](/docs/backup) have each command.
`playground ext` and `playground settings` write the folders themselves, so they need no Dashboard running; a usage error exits 2 and a refused write exits 1, with its reason.

## Accounts: `playground accounts`

`playground accounts list` prints each account the factory spends, a row of the `usage.accounts` setting: its provider, its email or label, whether the Keychain keeps its secret, and its last 5-hour and week reading. A GLM key reads both windows at 100% while its balance is empty, naming since when, and no reading after a failed usage read, as the sidebar shows them. It never prints a token or a key.
`playground accounts add --provider claude --email <email>` prints 3 steps (open the sign-in link in a private or guest window, sign in with the account to add, paste the code the page shows), runs `claude setup-token` in your terminal, then asks you to paste the token it printed, with no echo, and keeps it in the Keychain under `usage.keychainService` by that email.
`playground accounts add --provider glm --label <label>` asks for a Z.ai key the same way and keeps it under `models.glmKeychainService` by that label; `spawn.sh --backend glm --account <label>` runs on it, and the first GLM row is the default.
Adding an account that is already listed replaces its secret and leaves its row as it is.
`playground accounts remove <email|label>` drops the row and its Keychain item.
On Linux, which has no Keychain, each item is a file only you can read under `secrets/keychain/` in Playground's data folder.

## Yard: `playground yard`

`playground yard` reaches Yard, the hosted Playground's channels and DMs, from this Mac, with the address in `YARD_API_URL` and its approve pages at `YARD_WEB_URL`, read from your environment or the live dashboard checkout's `.env`.
`playground yard login` asks for a Yard token (`yard_...`), with no echo, checks it with Yard and keeps it in the Keychain under `playground-yard`, where the local Dashboard reads it too; `playground yard logout` removes it.
Make the token on Yard's Account page with its Relay switch on (`yard_relay_...`) to post from this Mac and let you read this Dashboard on Yard; with the switch off, the token only reads.
Once a day the Dashboard swaps that token for a fresh one of the same kind by itself, so you never make a new one: the old one stops working at the swap, and the Account page keeps the same token name.
`playground yard channels` lists your channels and DMs with their unread and mention counts.
`playground yard read <channel>` prints a channel's last 50 messages, oldest first, by `#name`, a DM's `@login` or an id, and leaves your unread counts as they are.
`playground yard post <channel> <text> [--kind <kind>]` posts as this Mac; a post Yard holds for your approval prints its approve page, and its card reaches your [Inbox](/docs/inbox) within a minute.
`playground yard bot add <name>` makes a bot on Yard, `<name>[bot]`, with its own DM with you and its own token, which goes straight into the Keychain item `playground-yard-bot-<name>` and never shows; it prints the item's name and the DM's id, and a reveal card in your [Inbox](/docs/inbox) copies the token for you to paste into the bot.
The bot's token reads and posts only in that DM; hand the bot [Connect a bot](/docs/yard-bot), which says how.
`playground yard bot add <name> --log` also lets the bot read your dispatcher's log through this Mac once you turn on the switch beside it on Yard's Account page, with every secret hidden first and each read noted in its DM; that switch, from your signed-in browser alone, turns it off or on again.
`playground yard bot revoke <name>` revokes it, stops this Mac answering its reads of the log and deletes its Keychain item; Revoke beside it on Yard's Account page revokes it on Yard alone, so run the command after it to delete the item and take the bot off this Mac's list of log readers too.

## Scripts: `playground ask`, `changelog`, `dm`, `ingest`, `queues`, `thread` and `wa`

Each runs the package script of the same name in the Dashboard's checkout, the one on branch `live.branch`, passing on every word after it, so `playground ask get #i12` is `bun run ask get #i12` there. The Dashboard's checkout holds the address of the database the Dashboard shows, so an item posted this way reaches your Inbox from any folder.

- `playground ask` posts an item to the [Inbox](/docs/inbox), reads its answer and closes it.
- `playground changelog` adds rows to the Changelog from GitHub's merges and versions, or a line by hand.
- `playground dm send <file>` posts the reply in the file, named by its absolute path, to your own Slack DM in Slack mode, framed, and records each post so the DM watch tells it from your messages.
- `playground dm upload <item id>` shares a Slack send's files into its channel and thread, a draft's words as their message, read from the answered Inbox item that id names; the Inbox runs it on Send or Approve.
  Both run the bundled Slack extension's scripts, which read the Slack token from the Keychain; with that extension off in Settings, either one says `Slack is not set up here` and runs nothing, and so does `dm send` with no DM set up (`slack.dmChannel` and `slack.dmOwner`), pointing you to the Inbox.
- `playground ingest` reads every Claude Code and Codex session Playground has run (every one on this machine with `PLAYGROUND_ALL_SESSIONS=true`) into the Dashboard's database; `--follow` keeps reading, and `status` says how far it is.
- `playground queues` prints the merge queue and the work queue.
- `playground thread` opens, routes, renames and lists the Inbox's threads.
- `playground wa send <file>` sends the reply in the file, named by its absolute path, to your WhatsApp through ops-wa, the WhatsApp link on a spare number, to your own number (`wa.owner`), or with `--to alert` to the number in `wa.alert`, a guest; it refuses a body holding a token shape, and says so when ops-wa is not running. Beside the reply it can send one more thing: `--file <path>` a photo, a video, a document or a voice note from the data folder's `wa/outbox/`, the reply its caption; `--location <lat>,<lon>` a location, the reply its name; `--quote <id>` a reply quoting a message of that chat from the last 24 hours, by its id; or `--edit <id>` and `--delete <id>` a fix or a take-back of a message it sent, by the id it printed. `--status` sends the reply as your one live status message, the 15-minute update: it edits the last one in place while that one is under 15 minutes old, WhatsApp's edit window, and fewer than 5 messages have come after it in your chat, sends a new one otherwise, and sends nothing when the words have not changed. In quiet hours, once you have read or written nothing for an hour, it holds the reply's text and prints `held for quiet hours`, and ops-wa sends the held texts as one catch-up when you read or write again or the window ends.
- `playground wa alert [--now-both] [--source <kind>:<ref>] <file>` sends an urgent alert to you at once and to the number in `wa.alert` after `wa.alertDelayMinutes`, unless you react on it or `wa.alertCheck` reads its source as handled; `--now-both` sends to both at once.
- `playground wa react <emoji> [--to alert] [--id <id>]` reacts on your latest WhatsApp message, the number in `wa.alert`'s with `--to alert`, or one of the last 24 hours by its id; the dispatcher reacts 👀 when a reply will take a while, and ✅ when none is needed.
- `playground wa status` prints whether each number has written or been approved, whether a reply can go to it now, when you last read ops-wa's messages, whether the last alert to the number in `wa.alert` was delivered and read, each pending alert, and the newest alert's outcome with its times: handled by the owner's reaction, handled at its source, sent to the second number, or a failed send with its reason, and for a `--now-both` alert or one that reached one number alone, where it went, or where it failed.
- `playground wa alert-set --from-owner-msg <id>` sets the second number (`wa.alert`) to the one phone number in your own WhatsApp message of that id, which ops-wa keeps for 24 hours.
- `playground wa relink` sets the old link aside after WhatsApp logged the device out, so ops-wa's next start posts a new pairing card.

## Troubleshooting

- **`factory is not running`** from `playground view`: run `playground`, which starts it, then `playground view` again.
- **`playground: no Dashboard checkout yet; run playground once to set it up`**: the Dashboard runs from a checkout of its own, on the branch the `live.branch` setting names, which a fresh install has not made yet. Run `playground`, which makes it and installs it, then run the command again.
- **`ops-dashboard's supervisor is not running`** or **`ops-dashboard's heartbeat is … old`** while `playground` waits: the Dashboard's background job stopped, so the Dashboard will not come up. Read `ops/dashboard/supervisor.log` under `~/.playground` for why, then run `playground` again.
- **`the Dashboard's stack could not start: <why>`** while `playground` waits: the Dashboard's background job tried to start it and it failed, for the reason it names. Fix that reason, such as starting Docker or OrbStack, then run `playground` again.
- **`portless does not route the Dashboard's addresses to its stack: <why>`** while `playground` waits: the Dashboard's background job checked portless's routes and found its address missing or pointing elsewhere, such as `no route for dashboard.playground.localhost in …/routes.json`. Read `ops/dashboard/supervisor.log` under `~/.playground` for why, then run `playground` again.
- **`the Dashboard's API answered 302 at <address>, a redirect to <address>`** while `playground` waits: it asked the Dashboard at an address portless serves another way, often `http` where portless serves `https`. Compare the two addresses it names, then run `playground` again.
- **`The dispatcher didn't start: spawn.sh refuses dispatcher: Claude Code would stop on its folder trust question in <folder>`** under Left for you, or from `playground dispatcher`: Claude Code asks whether you trust a folder before its first session there, and you have not said yes for Playground's folder yet, so Alpha would wait on that question. The install script says yes for the folder it cloned, so on a fresh install this shows only when it could not, with its reason under Left for you as **`Claude Code's trust of <folder>: <why>`**. On Claude Code's card in the Dashboard's first run, or in Settings > Harness, click **Trust this folder**, then start Alpha again ([Pick what Alpha runs on](/docs/install#pick-what-alpha-runs-on)).
- **`The Dashboard's database didn't start: <Docker's words>`** under Left for you: Docker refused to start the Dashboard's database or set it to start again after a restart. Run `docker ps -a` to see its container, start it with `docker start <name>`, then run `playground` again.
- **`the Dashboard did not answer within 15 minutes`**: its background job is still running but the Dashboard never answered. Read the same log, then run `playground` again.
- **`the Dashboard's supervisor is paused`**: someone paused updates on purpose. Remove the file the message names, then run `playground update` again.
